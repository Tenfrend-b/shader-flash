# 排查记录：进世界自动预编译的管线损坏，而 F8 手动预编译的没事

对外版本：**0.3.1**（玩家实测报告）。

## 1. 现象

* 玩家进入世界后，模组按配置里的副光影包**自动预编译**一条副管线；
* 这条自动预编译出来的管线**不能渲染实体**（切过去后实体消失）；
* 而在游戏里用 **F8 → 预编译 / 重建副管线** 手动重建同一条管线，就完全正常。

同一份代码、同一个包，只有“什么时候编译”不同 —— 说明差异在**环境状态**，不在编译流程本身。

## 2. 两套路径在代码上是同一个函数

```
进世界自动：onClientTick() → worldAutoBuildPending/reloadAutoBuildPending → ensureSecondary(false)
手动按钮  ：DuoConfigScreen 的按钮                                        → ensureSecondary(true)
```

`ensureSecondary(boolean report)` 里那个参数只是“要不要发聊天提示”，两条路径**后续完全相同**
（`startPrewarm` → 解包 → 解析 → `compilePrewarm`）。所以必须从**运行时机**上找差异。

## 3. 差异：编译时“主管线可能还没构造出来”

`ensureSecondary` 的前置检查只有：

```java
ShaderPack primaryPack = Iris.getCurrentPack().orElse(null);   // 只要 Iris 已经读到包
NamespacedId dimension = Iris.getCurrentDimension();           // 只要维度已知
```

它**不要求主管线（`IrisRenderingPipeline`）已经构造好**。而 Iris 是懒加载的：

* `Iris.getCurrentPack()` 在**解析完光影包**之后就有值；
* 各维度的管线是在**第一次要渲染那个维度**时才 `new IrisRenderingPipeline(...)`。

进世界 / Iris 刚重载时，模组是在“下一 tick”就开跑的（日志里
`Iris 已重载，副管线将在下一 tick 重建` 后面紧跟着 `开始预编译副管线 xxx`），
这一刻 `WorldRenderingSettings.INSTANCE` 里可能还是**默认值**：

| 字段 | 默认值 | 什么时候才被设成正确的值 |
| --- | --- | --- |
| `blockStateIds` / `blockTypeIds` | `null` | 管线第一次 `beginLevelRendering()`（且只在 `!initializedBlockIds` 时） |
| `entityIds` / `itemIds` | `null` | `IrisRenderingPipeline` 的构造函数 |
| `useExtendedVertexFormat` | `false` | `IrisRenderingPipeline` 的构造函数（`VanillaRenderingPipeline` 反而设成 `false`） |

## 4. 根因：用了“构造前的快照”去还原

0.3 及以前，`compilePrewarm` 在构造副管线前后是这么做的：

```java
WorldSettings snapshot = WorldSettings.capture();      // ← 上面那张表里的“当时值”
try {
    pipeline = new IrisRenderingPipeline(programSet);  // 构造函数会把全局值改成副包那一份
} finally {
    snapshot.restore();                               // ← 原样写回“当时值”
}
```

构造期间改写全局值是对的（构造函数本来就这么干），问题出在**还原**：
如果快照是在“主管线还没构造”的那一刻抓的，快照里就是上面那张表的**默认值**，
`restore()` 会把 `blockStateIds=null`、`entityIds=null`、`useExtendedVertexFormat=false` 写回去。

而 Iris 只在“新建管线”时设置这些值 —— 主管线早就初始化过了，它的
`beginLevelRendering()` 里那段 `if (!initializedBlockIds)` 不会再次执行。于是：

* **实体**：`useExtendedVertexFormat=false` 让顶点按**原版格式**写出，
  而着色器仍然是光影包的（按**扩展格式**读属性）→ 顶点属性全部错位 → **实体渲染不出来**；
  （这条正好是 `EntityShaderGuardMixin` 覆盖不到的**反方向**错配：它管的是“扩展顶点 + 原版着色器”。）
* 方块材质表被清成 `null`、实体/物品 ID 表也停在副包那一份 → 材质判定跟着一起不对。

手动（F8）路径为什么没事：**那时全局值一定是主管线的那一份**，
快照 = 当前值，`restore()` 等于空操作，所以两条路径表现不同。

## 5. 修法（0.3.1）

### ① 不再按快照还原，改成“按主管线的包重放一遍”

`DuoManager.restorePrimarySettings(...)`：

```java
WorldSettings.applyFor(primaryPack, Iris.getPipelineManager().getPipelineNullable(), dimension, false);
WorldRenderingSettings.INSTANCE.clearReloadRequired();
```

* 值全部来自**主管线的包**（方块材质表、实体/物品 ID 表、AO、分离 AO、方向性明暗、
  扩展顶点格式、分离实体绘制、体素化光源），因此**与构造先后无关**，一定是主管线那一份；
* 主管线此刻还没构造时也成立：`WorldSettings.applyFor` 现在允许 `pipeline == null`，
  其中“方向性明暗”按包自己的 `directives.isOldLighting()` 计算
  （`IrisRenderingPipeline#shouldDisableDirectionalShading()` 返回的就是 `!oldLighting`）；
* `clearReloadRequired()` 吃掉构造函数留下的假“需要重载”标志，避免白白全区重建；
* 只有连主管线的包都拿不到时才退回快照（此时快照也不会比默认值更糟）。

### ② 加一道不变量安全网

`DuoManager.keepExtendedVertexFormat()`（每 tick 一次，一个 boolean 比较）：

> 只要当前管线是 **光影管线**，全局 `useExtendedVertexFormat` 就必须是 `true`；
> 发现被写成就地校正，并打一条 WARN（只打一次），方便判断还有没有别的路径在写坏它。

这条不变量是 Iris 自己的（只有 `VanillaRenderingPipeline` 会设成 false），
所以校正它不会与 Iris 冲突；它保证**同一类错配以后不会再出现**。

## 6. 怎么验证

1. 进世界（自动预编译），切到副管线 → 实体应当正常；
2. 日志里不应再出现 `全局「扩展顶点格式」被写成了 false`；
3. 想看得更细：`-Dshaderflash.debug`（或日志级别调到 DEBUG）后，`预编译后全局材质设置`
   那条 DEBUG 会打印 `扩展顶点格式 / 方块材质表 / 实体ID表` 三项 —— 都应当是 `true`。
4. 兼容性自检里的「扩展顶点格式(全局)」也应当显示 `true`。

## 7. 后续：0.3.2 直接删掉了自动预编译

上面那两条修复（重放主管线设置 + 不变量安全网）之后，玩家实测**仍然**能在
“进世界自动预编译”这条路径上遇到实体渲染不出来的问题，所以按玩家要求改成了更彻底的做法：

* **删除**进世界自动预编译（`autoBuildOnWorldJoin`）与 Iris 重载后自动重建
  （`rebuildAfterIrisReload`）两个开关、两个 `*AutoBuildPending` 标志、以及
  `onClientTick` 里那段“自动建/重建”的判断（顺带清掉了只为它服务的
  `tickCounter` / `nextBuildAttempt` 退避字段）；
* `onIrisPipelinesDestroyed()` 现在只**释放**副管线，日志写
  `Iris 已重载；副管线已释放，需要时请手动预编译`；
* **换维度**也不再自动重建：释放旧维度的副管线并提示玩家
  （`MESSAGE_PRELOAD_AFTER_DIMENSION_CHANGE`）；
* 于是副管线只在这三种**玩家主动**的时机构建：设置界面的「预编译 / 重建副管线」按钮、
  按下 F7 时若还没有可用副管线（就地构建）、打开双管线总开关。

换句话说：**玩家必须自己手动预编译**，这条路径（世界已经跑起来、玩家主动触发）
正是实测中一直正常的那个时间窗。
