# 排查记录：F7 切换后「材质 ID」与「地形着色器」不同步

回报的两个现象：

1. **按 F7 切换主副后，实体渲染异常，表面出现闪烁的高饱和度彩色色块。**
2. **副管线预编译的 P 光影切为主管线后，没有播植被摇动动画**；
   而用 Iris 自己的界面把当前光影切成同一个 P 时，摇动是正常的。

结论：这是**两个独立的缺陷**，都出在“把已经存在的管线提升为主管线”这条路上。
两个缺陷的共性是：**Iris 有一些与光影包相关的状态，要么被缓存/捕获、要么被编译期烘焙，
而本模组在切换时只更新了全局设置表，没有把这些副本一起刷新。**

---

## 一、现象 2 的根因：区块构建捕获了一份旧的方块 ID 表

### 证据链

**① Iris 在 `ChunkBuildBuffers` 构造时把表存进 `BlockContextHolder`**

`net.irisshaders.iris.compat.sodium.mixin.block_id.MixinChunkBuildBuffers`：

```java
@Inject(method = "<init>", at = @At("RETURN"), remap = false)
private void iris$onConstruct(ChunkVertexType vertexType, CallbackInfo ci) {
    Object2IntMap<BlockState> blockStateIds = WorldRenderingSettings.INSTANCE.getBlockStateIds();
    if (blockStateIds != null) {
        this.contextHolder = new BlockContextHolder(blockStateIds);   // ← 捕获当时的表
    } else {
        this.contextHolder = new BlockContextHolder();
    }
}
```

**② 这个对象的生命周期是“整个世界会话”**

`me.jellysquid.mods.sodium.client.render.chunk.RenderSectionManager:89`

```java
this.builder = new ChunkBuilder(world, ChunkMeshFormats.COMPACT);
```

`ChunkBuilder` → `ChunkBuildContext` → `new ChunkBuildBuffers(vertexType)`（每线程一份），
而 `RenderSectionManager` 只在**世界加载 / 整世界重载**时创建。
也就是说：**从进入世界到下一次整世界重载之间，所有区块构建用的都是这份捕获的表。**

**③ 取值处**（`BlockContextHolder.set`）：

```java
public void set(BlockState state, short renderType, byte lightValue) {
    this.blockId = (short) this.blockStateIds.getOrDefault(state, -1);   // ← 永远查捕获的那份
    ...
}
```

**④ 于是本模组的“逐区块后台重建”白做了**

切换主副时我们做的是：更新全局表 → `scheduleRebuildForChunks(...)`。重建确实发生了
（日志里是 `已把 32856 个区块段排队后台重建`），但重建读取的是**捕获的那份旧表**，
所以写入顶点的 `mc_Entity.x` 仍然是旧光影包的材质 ID。

**⑤ 为什么“用 Iris 界面切换就正常”**

那样会走 Iris 自己的重载：`destroyPipeline()` → 重建管线 → `beginLevelRendering()` 里
`allChanged()` → **重建 `RenderSectionManager`** → `ChunkBuildBuffers` 重新构造 → 拿到新表。
这与用户观察到的“界面切正常、F7 切没有摇动”完全吻合。

**⑥ 为什么摇动动画会“永远不回来”**

Photon（`include/vertex/utility.glsl`）用材质掩码决定哪些方块要摇：

```glsl
uint get_material_mask() {
#if defined PROGRAM_GBUFFERS_TERRAIN || defined PROGRAM_GBUFFERS_WATER
    return uint(max0(mc_Entity.x - 10000.0));   // ← 来自顶点里的方块 ID
```

`displacement.glsl` 里的 `WAVING_PLANTS` / `WAVING_LEAVES` 只在
`PROGRAM_GBUFFERS_TERRAIN` 下生效，且判定的就是 `material_mask`。
ID 一直是旧包的 → 掩码永远匹配不上 → 不摇。

### 运行时验证

`tools/BlockIdRefreshTest.java` 用**真实的** Iris `BlockContextHolder` 复现了这个流程：

```
旧包给石头的材质 ID        : 5000
新包给石头的材质 ID        : 10001

未修复：重建网格写入的 ID  : 5000   <- 仍是旧包（光影包的材质判定会失配）
已修复：重建网格写入的 ID  : 10001  <- 取到新包（材质判定与摇动动画恢复）
```

### 修法

新增条件加载的 `BlockContextHolderMixin`：把 `set(...)` 里那次取值改成读**当前**的表。

```java
@Redirect(method = "set", at = @At(value = "INVOKE",
    target = "Lit/unimi/dsi/fastutil/objects/Object2IntMap;getOrDefault(Ljava/lang/Object;I)I"))
private int shaderflash$useCurrentBlockStateIds(Object2IntMap<BlockState> captured, Object state, int fallback) {
    Object2IntMap<BlockState> current = WorldRenderingSettings.INSTANCE.getBlockStateIds();
    return (current != null ? current : captured).getOrDefault(state, fallback);
}
```

* `@Redirect` 的目标已对着 Iris 1.7.2 的真实字节码逐字段核对：
  `invokeinterface it/unimi/dsi/fastutil/objects/Object2IntMap.getOrDefault:(Ljava/lang/Object;I)I`；
* 这个 mixin 由 `DuoMixinPlugin` 条件加载（没装 Sodium、或 Iris 没有 Sodium 兼容层就跳过）；
* 万一某个环境加载不了它，`remeshFor(...)` 会检测到并**退回整世界重载**，
  绝不留下“网格一直用旧 ID”的状态。

## 二、现象 1 的根因：地形着色器把「分离 AO」烘焙进了源码

### 证据链

**① Iris 在编译地形着色器时读全局设置并写进源码**

`net.irisshaders.iris.pipeline.transform.transformer.SodiumTransformer`：

```java
public static void injectVertInit(ASTParser t, TranslationUnit tree, Root root, SodiumParameters parameters) {
    String separateAo = WorldRenderingSettings.INSTANCE.shouldUseSeparateAo()
        ? "a_Color" : "vec4(a_Color.rgb * a_Color.a, 1.0)";     // ← 拼进着色器源码
    ...
}
```

这是整个 `transform` 包里**唯一**读取全局设置的地方；也就是说：**这个值在着色器编译期就定死了。**

**② 副管线的地形程序是在“主管线的全局值”下编译的**

副管线预编译时我们刻意不改变全局状态（这是设计的一部分：材质表以主管线为准），
于是它第一次渲染地形（幽灵渲染那一遍）时执行的
`IrisChunkProgramOverrides.createShaders(...)` → `SodiumTerrainPipeline.patchShaders(...)`
读取的是**主管线**的 `shouldUseSeparateAo`。

**③ 用户这次的两个包恰好在这项上不同**

日志原文：

```
[ShaderFlash] 两包差异（方块材质 ID 表、分离 AO），已把 32856 个区块段排队后台重建（无可见卸载）
[ShaderFlash] 已切换到 photon_v1.3b，耗时 48 ms
```

切换时我们把全局值改成了新包的，并重建了区块网格（顶点数据用新取值），
但**缓存里的地形程序仍然带着旧包的取值** —— 顶点数据与着色器对不上。

**④ 为什么“重启 / 用 Iris 界面切换”不会有这个问题**

那两条路都会让 Iris 重编地形程序（`destroyPipeline()` 会 bump 版本计数器，
而 `IrisChunkProgramOverrides.getProgramOverride` 一发现计数器变了就 `deleteShaders()`）。

### 修法

切换时，**如果两个包在“会被烘焙进着色器”的设置上不同，就 bump 一次版本计数器**，
让 Iris 丢掉地形程序并在新取值下重编：

```java
if (rebuild && before.requiresShaderRecompile(after) && FabricLoader.getInstance().isModLoaded("sodium")) {
    int counter = accessor.shaderflash$getVersionCounter();
    accessor.shaderflash$setVersionCounter(counter + 1);
}
```

* `requiresShaderRecompile` 目前只比较「分离 AO」——它是当前 Iris 唯一会烘焙进源码的全局设置；
* 条件是 `rebuild`（也就是确实要重建区块网格）：只重编着色器而不重建顶点数据，
  同样会造成两边不一致，反而更糟；
* 代价是这一种情况下切换会多花一次地形程序编译（约 6 个程序）。
  这是 0.1.3 之前刻意省掉的优化（旧版代码注释里写着“不再 bump 计数器”），
  但那个优化建立在一个错误前提上——它假设“重建网格就等于管线状态一致”。

## 三、要验证什么

1. **植被摇动**：C 为主、P 为副 → F7 切到 P → 看草/树叶是否摇动。
   修复后应当立刻恢复（不需要重进世界）。若仍不摇，请开「兼容性自检」，
   看 `副管线槽位`、`方块材质 ID 表` 的提示，并把日志发我。
2. **画面明暗/材质**：同样切到 P，观察方块表面是否正常（不再出现成片的异常色块）。
3. **切换耗时**：用两个 block.properties 不同的包互切时，日志里会多一行
   `两包在"会被烘焙进地形着色器"的设置上不同（分离 AO），已让地形程序重编一次`，
   此时切换会比以前慢一点（多一次地形程序编译），这是预期的。
4. **主菜单归来**：退出世界后显存是否回落（0.1.2 的修复）。

## 四、还没完全确认的部分

现象 1 用户描述为「**实体**表面出现色块」。本次修复的②是**地形**侧的
“顶点数据与地形着色器不一致”，它是可证的；而实体自身走的路径
（`entityId` / `currentRenderedItemId` / 顶点格式）经查**全部是每帧从全局表取值**，
不存在同类缓存。因此有几种可能：

* 用户看到的其实是受地形数据影响的画面（Photon 的延迟着色 / 体积光 / 反射会读取地形材质）；
* 或者是另一个我们尚未定位的问题。

如果 0.1.3 之后仍有该现象，请提供：**一张截图**、以及当时的主/副光影包名，
我据此继续定位（截图能立刻区分“实体自身渲染错”还是“环境光照错”）。
