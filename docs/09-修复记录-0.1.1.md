# 0.1.1 修复记录

接手本模组后做的一轮 bug 修复。**只改正确性，不加新功能**。

四条问题的共同点是：都发生在“副管线那一遍”或“临时切换”的收尾上，
而副管线的输出从不上屏，所以前两条在画面上完全看不出来。

---

## ① 幽灵渲染的视角被叠加了两次相机旋转

### 证据

1.20.4 反编译源码 `net.minecraft.client.renderer.GameRenderer`：

```java
public void render(float tickDelta, long startTime, boolean tick) {
    ...
    this.renderLevel(tickDelta, startTime, new PoseStack());   // ← 每帧新建，用完即弃
    ...
}

public void renderLevel(float tickDelta, long limitTime, PoseStack stack) {
    ...
    PoseStack projection = new PoseStack();
    ...
    stack.mulPose(Axis.XP.rotationDegrees(camera.getXRot()));          // ← 直接改调用方的栈
    stack.mulPose(Axis.YP.rotationDegrees(camera.getYRot() + 180.0F));
    ...
    this.minecraft.levelRenderer.renderLevel(stack, ...);              // 视图矩阵就是它
}
```

`renderLevel` 内部没有为这两次 `mulPose` 配对的 push/pop——原版不需要还原，
因为调用方传进来的是一个临时对象。而本模组在 `renderLevel` 的 **TAIL** 拿到的是
**同一个已被改写过的栈**，直接再调一次 `renderLevel`，于是相机旋转被应用了两次。

Iris 的 `MixinLevelRenderer.iris$setupPipeline` 也在 HEAD 处用
`CapturedRenderingState.setGbufferModelView(poseStack.last().pose())` 读这个栈，
所以副管线那一遍的 `gbufferModelView` 同样是被叠加过的。

### 修法

> **注意：本节的修法在 0.1.1 初版里写错过，已由 0.1.2 修正。**
> 初版用的是 `matrices.push()` / `matrices.pop()`，结果启用双管线后一进世界就崩：
> 原版 `LevelRenderer.renderLevel` 中段会调 `checkPoseStack()`，它要求传入的栈
> **只有 1 帧**（`PoseStack.clear()` = `poseStack.size() == 1`），push 会让它抛
> `IllegalStateException: Pose stack not empty`。详见 [`CHANGELOG.md`](../CHANGELOG.md) 的 0.1.2 一节。

0.1.2 起改为「入口采样 + 另建一个栈」，**完全不动原版那个 PoseStack**：

```java
@Inject(method = "method_3188", at = @At("HEAD"), remap = false, require = 1)
private void shaderflash$capturePose(float tickDelta, long limitTime, MatrixStack matrices, CallbackInfo ci) {
    DuoManager.captureEntryPose(matrices);          // 只记下顶层姿态的副本
}

@Inject(method = "method_3188", at = @At("TAIL"), remap = false, require = 1)
private void shaderflash$afterWorldRender(float tickDelta, long limitTime, MatrixStack matrices, CallbackInfo ci) {
    DuoManager.onWorldRenderTail(...);
}
```

`DuoManager.onWorldRenderTail` 在真正要渲染副管线时：

```java
MatrixStack ghost = new MatrixStack();                 // 只有 1 帧，checkPoseStack 通过
ghost.peek().getPositionMatrix().set(entryPose);       // 内容 = renderWorld 入口时的姿态
ghost.peek().getNormalMatrix().set(entryNormal);
renderer.renderWorld(tickDelta, limitTime, ghost);
```

于是两条管线得到的视图矩阵逐元素相同，而原版那个栈从头到尾没有被我们改过。

### 数值验证

`tools/RotationTest.java` 直接用真实的 `MatrixStack`（来自 named MC jar）复现这个流程：

```
reference (one pass)          : [+0.7314, -0.2719, +0.6254, +0.0000]
reuse caller stack (broken)   : [+0.1083, -0.6307, +0.7684, +0.0000]
fresh stack from entry (0.1.2): [+0.7314, -0.2719, +0.6254, +0.0000]

reuse caller stack: view == reference ? false
fresh stack       : view == reference ? true

push/pop 方案: checkPoseStack 会通过吗 ? false   (false = 会抛 Pose stack not empty)
fresh 栈     : checkPoseStack 会通过吗 ? true
```

运行方式见 `tools/README-工具.md`。

## ② 副管线截图之后视锥体 / 遮挡剔除不复原

Iris 的 `MixinLevelRenderer.iris$setupPipeline`（`WorldRenderer.render` HEAD）会：

```java
if (pipeline.shouldDisableFrustumCulling()) {
    this.cullingFrustum = new NonCullingFrustum();
}
Minecraft.getInstance().smartCull = !pipeline.shouldDisableOcclusionCulling();
```

它**从不还原**这两个状态——正常路径上不需要，因为下一帧还会按当时的管线重新设一次。
但本模组会临时把“当前管线”换成副管线（截图）或者渲染一整遍副管线（幽灵渲染），
如果不还原，主管线就会继承副管线的剔除设置。

幽灵渲染那条路已经手动还原了（`WorldRendererAccessor` + `client.chunkCullingEnabled`），
截图的 `begin/endScreenshotSwap` 漏了。

**后果**：用声明了 `frustum.culling = false` 的光影包（Iris 的 `shouldDisableFrustumCulling()`）
截一次图，主管线之后会一直全量渲染所有区块，直到重载世界。

**修法**：`beginScreenshotSwap` 快照视锥体与 `chunkCullingEnabled`，
`endScreenshotSwap` 在还原管线之后一并还原，并在 `finally` 里复位 `ShadowRenderer.ACTIVE`。

> **0.1.9 现状**：截图已经改成**完全不切屏**（像素直接读副管线的离屏 FBO），
> 那条路径根本不再改“当前管线”，所以 `begin/endScreenshotSwap` 连同这两行还原逻辑
> 一起被删掉了。本节记录的是历史修复；幽灵渲染那条路的还原依然保留在
> `DuoManager.onWorldRenderTail` 里，仍然是必需的。

## ③ `rebuildAfterIrisReload` 从未生效

全仓只有一处读它——`onIrisPipelinesDestroyed()` 里的一句日志：

```java
if (DuoConfig.get().enabled && DuoConfig.get().rebuildAfterIrisReload) {
    ShaderFlash.LOGGER.info("[ShaderFlash] Iris 已重载，副管线将在下一 tick 重建");
}
```

而真正决定要不要重建的是 `onClientTick` 里的 `config.autoBuildOnWorldJoin`。
所以 `docs/02-配置项.md` 描述的“Iris 重载后是否自动重建副管线”并没有实现。

**修法**：拆成两个独立的待办标志

| 标志 | 置位时机 | 受哪个开关控制 |
| --- | --- | --- |
| `worldAutoBuildPending` | 刚进入世界 | `autoBuildOnWorldJoin` |
| `reloadAutoBuildPending` | Iris 重载（`destroyPipeline`） | `rebuildAfterIrisReload` |

另外把“换维度”单独处理：现有副管线的维度与当前维度不一致时无条件重建
（原先这条也搭在 `autoBuildOnWorldJoin` 上，关掉该开关后换个维度副管线就永久失效）。

## ④ 离屏 FBO 从不解散

`GhostFramebuffer.destroy()` 此前没有任何调用点；`DuoManager.destroySecondary()`
只调 `pipeline.destroy()`。关掉双管线或离开世界后，
那块与主帧缓冲同尺寸的彩色 + 深度离屏缓冲会一直占着显存，
而 README 写的是“关闭时副管线资源会被释放”。

**修法**：新增 `DuoManager.releaseGhostTarget()`，在这两个时刻调用：

* `onEnabledChanged()` 关闭双管线时；
* `onClientTick()` 检测到世界已卸载时。

它内部会先检查 `ghostPassActive`，保证不在渲染中途删除 GL 资源。

## 如何复现与验证

```powershell
# 1) 离线构建 + 校验（不需要网络 / Gradle）
powershell -ExecutionPolicy Bypass -File build-local.ps1 -Version 0.1.2

# 期望输出末尾：
#   VERIFY PASSED
#   DONE -> build\out\shader-flash-0.1.2.jar

# 2) 数值验证 PoseStack 修复
powershell -ExecutionPolicy Bypass -File tools\run-rotation-test.ps1

# 3) 校验器报告
#   build\verify-report.txt 末行应为「结果：全部通过」
```

### 静态校验覆盖到什么程度

`VerifyTool` 会检查：

* 8 个 mixin 的目标类是否存在；
* 每个 `@Inject` / `@Accessor` / `@Shadow` 指向的成员是否存在；
* **注入处理器的参数描述符是否与目标方法一致**（参数写错会让注入静默失效）；
* 模组字节码里每一个类引用能否在运行期类路径（intermediary）里解析。

本次校验用 26413 个类的类路径，0 处未解析引用。
注意：故意**不**把 Yarn 命名的 Minecraft jar 放进校验类路径——
否则“重映射漏了、还留着 named 引用”会被掩盖成通过。

### 真机需要重点看什么

1. **开双管线后主画面是否正常**（副管线那一遍的视角修复后，阴影贴图与区块剔除的负担会变正常，
   理论上帧率比修复前更稳定；如果之前用「每帧」模式觉得特别卡，现在可以再测一次）；
2. **F2 副管线截图**：开「副管线截图」，用 BSL 这类包（它声明了 `frustum.culling = false`）
   截一张图，然后**关掉该功能并正常游玩**，确认没有出现“所有区块都画”的性能异常；
3. **Iris 重载**：把「重建后自动重建」关掉，按 R 重载光影，确认副管线**不会**自动重建
   （设置界面底部会显示副管线槽位为空）；再打开开关重载一次，确认会重建；
4. **离开世界后显存**：开过双管线再退回主菜单，观察显存占用是否回落
   （修复前那块离屏 FBO 会一直留着）。
