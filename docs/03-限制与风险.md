# 限制与风险

## 1. 性能：这不是“免费的第二条管线”

副管线那一遍是**完整的**一帧世界渲染：阴影贴图、几何、天空、天气、实体、粒子、手部，
以及 Iris 的全部后处理链。

* **平时不渲染（0.2.2 起）**：副管线只保持“编译好、资源就绪”，不做副管线截图时
  完全不产生 GPU 开销；切换（F7）依然只是交换指针。
* **截图时会渲染若干帧**：预热帧数（默认 20）加上取景那一帧，帧率会在这一小段时间里
  掉到一半左右 —— 这是取景必须付的代价（见 `17-…` 与 `08-…`）。
* **高清档位更重**：`screenshotLongEdge` 选到 2560/3840 之后，副管线要按目标尺寸
  重建一整套渲染目标，显存与那一帧的耗时都会明显上升。核显（本机是 Intel Iris Xe）
  建议先试 1920~2560，觉得吃力就退回「跟随窗口」。

## 2. 显存

副管线需要自己的一整套渲染目标（多个 colortex + 深度）、阴影贴图、以及全部着色器程序。
1080p 下这个开销通常在几百 MB 量级，取决于光影包的 `renderTargets` 声明与阴影分辨率。

## 3. 两条管线共享的全局状态（重要）

以下状态在 Minecraft 里是**全区共享**的，不区分管线：

| 状态 | 后果 |
| --- | --- |
| 区块顶点里的**方块材质 ID** | 两包 `block.properties` 不同时，副管线那一遍材质判断会偏 |
| **扩展顶点格式**开关 | 由主管线决定，副包若需要不同格式则不会生效 |
| AO 等级、体素化光源方块、实体分离绘制 | 本模组会快照/还原，副管线那一遍用主管线的值 |

后果是：**副管线那一遍的画面可能与它单独作为主管线时并不完全一致**（材质分配层面）。
这不影响你看到的画面（不上屏），但意味着：

* “预热”在材质层面不是 100% 等价；
* 真正切到副包时，如果材质表不同，Iris 会重建一次区块网格 —— 那部分延迟省不掉。

设置界面的**兼容性自检**会逐项列出两包的差异（AO、体素化、实体分离绘制、阴影分辨率、
方块材质 ID 表），据此你可以判断这两包是否适合同时驻留。

## 4. 切换时剩下的开销

| 开销项 | 是否还有 | 说明 |
| --- | --- | --- |
| 解析光影包、编译全部着色器 | 否 | 预编译阶段已经做完 |
| 分配渲染目标 / 阴影贴图 | 否 | 已经分配并常驻 |
| Sodium 地形着色器 | 是 | 6 个左右的地形程序；本模组已为主副各留缓存，通常只剩“换一份缓存” |
| 重建区块网格 | 视情况 | 只有两包材质 ID 表不同才会发生 |

## 5. 兼容性

* **老光影包的保留字冲突：0.1.9 起不再处理，这是刻意的。** Iris 1.7.1 起会把所有包转译成
  `#version 410 core`，于是老包里像 `sample` 这种变量名会直接编译失败。曾经的「兼容
  GLSL 4.x 保留字」只是在副本上改名，让编译能过去 —— 但这类代码能跑的语义本来就依赖
  旧版 GLSL，换个名字并不等价，而且**默认加载不了的光影包玩家根本不会去用**，
  所以功能已整体删除（源码、界面开关、缓存戳记一并删掉）。
  这类包只能由作者自己更新；编译失败时聊天框与日志仍会给出对应提示
  （见 `ShaderErrorHints`）。

* **副管线预编译仍有一次卡顿**：解包已移到工作线程，但解析与着色器编译都必须留在渲染线程
  （Iris 解析 `shaders.properties` 时会做 GL 查询，编译更是在管线构造函数里直接调 GL；
  详见 [`12-…`](12-排查记录-预编译与截图-0.1.9.md)）。
* **Iris 的阴影渲染目标是懒创建的**：`shadow.enabled` 没写、又没有非 Sodium 版程序用到阴影采样器时，
  它到 Sodium 懒编译地形程序那一步才会 `requireNonNull` 失败（MakeUp 就是这种情况）。
  本模组在构造副管线时会按“这个包是否带阴影程序”补建，其它模组/环境不受影响。
* **副管线截图期间可能看到地形材质分类变化**：两包材质表不一致时，截图前必须把材质表切到
  副包并重建网格，而区块网格是全区共享的 —— 这是 Minecraft 单套网格的固有限制。
  两包材质设置一致时不会有任何可见变化。

* **版本绑定**：注入点按 Iris 1.7.1 / 1.7.2+mc1.20.4 的真实成员写死。已验证这两个版本；
  再往上的版本如果改了这些成员名，注入会失败。
* **失效时的行为**：`getFramebuffer()` 重定向没生效时，模组会判定副渲染会把画面画到屏幕上，
  于是**立即停用副渲染**并给出聊天提示，而不是让画面反复闪烁。可用设置里的
  “解除副渲染停用”重试。
* **其它改 Iris 内部状态的模组**：例如另一个也去换 `PipelineManager.pipeline`、
  或自行构造 `IrisRenderingPipeline` 的模组，可能与本模组冲突（顺序与状态归属会互相踩）。
* **Sodium**：已适配（地形程序双份缓存）。未装 Sodium 时地形走 Iris 自己的 per-pipeline
  `ShaderMap`，切换本来就是零编译。

## 6. 没做到的部分（说清楚）

### 「副管线截图偶发偏黑」：**这是光影包自己的显示策略，不是本模组的问题**（0.1.17 定案）

现象：以 MakeUp（MFU）这类包为副包时，F2 偶尔拍到一张**明显偏黑**的 PNG。

**玩家实测结论（2026-09-13，0.1.16）**：与本模组的工作原理无关——
**MFU 刚加载时默认画面亮度极低，需要继续渲染 10~20 帧，亮度才会被它自己的“人眼适应”抬到可用水平。**
也就是说这是**光影包的显示策略**（模拟人眼适应），模组只是“拍得太早”。

对应措施（0.1.17）：

1. 取景前先让副管线连续渲染 **`screenshotWarmupFrames`（默认 20 帧，设置界面可调 0~60）**，
   再按快门——正好覆盖 MFU 的适应期；
2. 仍保留：先要求副管线渲染过至少一整帧（`PackSlot.renderedOnce`，保证 Iris 的
   composite/final 翻转状态已经跑起来）、以及 `isRemeshSettled()` 之后再等 500 ms
   才取景（避免“视距内那一批刚建完就抢拍”）；
3. 截图等待期间 HUD 会显示**区块重建进度（已做/总数 + 百分比 + 进度条）与预热帧数**，
   玩家可以自己判断什么时候按快门最合适。

> 历史记录：0.1.12 曾用“抓完检测是否全黑再重拍”来兜底（针对性太强、可维护性差，已删除）；
> 0.1.13 把原因猜成“新管线的第一帧 / 刚重建完就抢拍”，只覆盖了其中一部分。
> 0.2 又删掉了“等太久就按当前画面拍”的超时回落（有进度条之后没有意义，且只会拍到半成品）。
> 现在按玩家实测结论处理，见 [`17-功能-截图副管线性能调度与截图进度.md`](17-功能-截图副管线性能调度与截图进度.md)。

* **无法让第二条管线“完全独立”**。要做到真正的独立（各自独立的全局材质表、独立的顶点格式、
  可并行提交给 GPU），需要改 Iris 本体把 `WorldRenderingSettings` 之类的全局单例拆成
  每管线一份。作为附属模组，本方案是在 Iris 现架构上能拿到的最小侵入实现。
* **没有真机运行验证**。本次交付是在离线环境里完成的：编译、重映射、注入点与引用校验都做了
  （见 `docs/04-构建与验证.md` 与 `docs/verification/`），但没有启动 Minecraft 跑图。

## 7. 出问题时怎么排查

1. 看 `.minecraft/logs/latest.log` 里 `[ShaderFlash]` 开头的行；
2. 聊天框里的提示（可关）；
3. 设置界面底部会显示当前状态、上次切换耗时、以及最后一次错误原因；
4. 如果副渲染被自动停用，先确认 Iris 版本是 1.7.x；
5. 关掉双管线后依然异常，说明问题与本模组无关（副管线已释放）。
