# 配置项参考

配置写在 `.minecraft/config/shaderflash.json`，所有项都能在设置界面里改（改完立即保存）。

| 字段 | 界面名 | 默认 | 说明 |
| --- | --- | --- | --- |
| `enabled` | 双管线 | `false` | 总开关。关闭时副管线资源会被释放 |
| `secondaryPack` | （左侧列表） | `""` | 副光影包名；目录名或去掉 `.zip` 的文件名 |
| `keepOldPrimaryAsSecondary` | 保留旧主包为副包 | `true` | 互换后把原主管线留作副管线，反向切换也零编译 |
| `chatFeedback` | 聊天提示 | `true` | 预编译、切换、自检结果是否发到聊天框 |
| `hudStatus` | HUD 状态 | `false` | 左上角显示主/副包、副渲染截图分辨率、副管线耗时 |
| `initialWarmupRender` | 新管线初始化渲染（调试） | `true` | 新管线建好后是否补渲染一帧（离屏）。**默认开 = 一直以来的行为**；关掉可省掉这一整遍世界渲染（预编译刚结束时更顺），代价是这条管线在被真正用到之前一帧都没画过 —— 可能 F7 切过去的第一帧是黑的，第一次切换还要现编译地形程序。出事把开关打回去即可（不需要换版本） |
| `backgroundPrewarm` | 后台预编译 | `true` | 预编译副管线时把「**解包**」放到工作线程，界面显示进度；关掉则退回一口气同步完成。**0.2 起它只管解包这一件事**：解析与着色器编译都必须在渲染线程、且都是原子的（实测 Iris 解析期会做 GL 查询，见 [`12-…`](12-排查记录-预编译与截图-0.1.9.md)），不再有任何“调度”它们的档位 |
| `remeshPolicy` | 截图副管线性能调度 | `2`（中负载） | `0`=极低负载（300 段/tick）、`1`=低负载（700）、`2`=中负载（1500）、`3`=高负载（4000）、`4`=最大负载（一次性）。**只影响「副管线截图」取景前那一轮“切到副包材质”的区块重建节奏**；F7 主副互换与截图后的材质还原一律一次性投完，与该字段无关。字段名在 0.2 由 `prewarmPolicy` 改名而来，旧值不再读入（回到默认「中负载」）。详见 [`17-…`](17-功能-截图副管线性能调度与截图进度.md) |
| `screenshotWarmupFrames` | 取景预热帧数 | `20` | 「副管线截图」按快门前先让副管线完整渲染多少帧。玩家实测：MakeUp 这类包刚加载时画面亮度极低，要连续渲染 10~20 帧、等它自己的“人眼适应”把亮度拉起来才可用（属光影包的显示策略，与本模组无关） |
| `noFrameTimeoutTicks` | 最大静默等待时间 | `100` | 截图等待期间，**连续多少 tick 一帧都没渲染出来**（窗口最小化 / 渲染卡死）才取消本次截图。这不是超时回落（0.2 已删），而是收尾——否则按 F2 会永远卡在等待状态。可调区间 **100 ~ 32767 tick**（20 tick = 1 秒；32767 ≈ 27 分钟，等于调试时基本不会触发）。越界值会被自动夹回区间 |
| `screenshotWidth` / `screenshotHeight` | 副渲染截图分辨率（宽 / 高） | `0` / `0` | 两个都是 `0` = 跟随窗口分辨率（默认，渲染进主帧缓冲）。填了之后副管线那一遍渲染进**副管线自己的目标**（真实主帧缓冲一个像素都不动）；只填一边时另一边按窗口宽高比推出（界面里也有两个按钮做同一件事）。单边区间 `64 ~ 16384`；像素总量超过约 33M（7680×4320）**只警告，不限制** —— 照样按玩家填的尺寸渲染，风险由玩家承担。分辨率越高越占显存，那一帧也越慢 |
| `vanillaPackEntry` | 「空包」光影包条目 | `true` | 在 `shaderpacks/` 下维护一个叫 `原版` 的目录型光影包（不含任何程序 → Iris 合成原生等价的 fallback 着色器），让「空包」能作为一条管线参与双管线。关掉就不再生成，已生成的不会删；详见 [`13-…`](13-功能-空包光影包.md) |
| `rebuildChunksOnSwitch` | 切换时重做区块网格 | `true` | 两包在“会被烘焙进网格”的设置上不同时才需要；关掉则切换永远零重建 |
| `seamlessRemesh` | 逐区块后台重建（无感） | `true` | 需要重建时走 Sodium 的逐区块排队重建（看不到卸载）；关掉则退回一次性整体重建 |
| `secondaryScreenshot` | 副管线截图（F2 用副管线） | `false` | 开启后 F2 由本模组接管：先把材质表切到副包并等地形重建完，再在**某一帧的开头**用副管线渲染一遍、读像素存盘（按 `screenshotWidth` / `screenshotHeight` 决定分辨率），拍完自动还原。取景那一帧玩家看不到；两包材质表不一致时，重建期间屏幕上的地形会跟着换成副包的材质分类。文件里不含 HUD |
| `screenshotJpg` | JPG 模式（压缩截图） | `false` | 开启后副管线截图存成 **JPG（质量 85%）**而不再是无损 PNG：体积明显更小，代价是有损压缩（边缘有压缩痕迹），文件名后缀 `.jpg`。像素来源与 PNG 路径完全相同（同一个 `ScreenshotRecorder.takeScreenshot`），只是换了编码器；编码与写盘在 IO 工作线程上做，不卡游戏。只影响本模组接管的 F2，不影响原版截图 |

> **0.3.2 起没有任何自动预编译**：`autoBuildOnWorldJoin`（进世界自动预编译）与
> `rebuildAfterIrisReload`（Iris 重载后自动重建）两个字段**已删除**。
> 副管线只在这三种**玩家主动**的时机构建：① 设置界面里的「预编译 / 重建副管线」按钮；
> ② 按下 F7 时若还没有可用副管线（就地构建）；③ 打开双管线总开关。
> 换维度会把旧维度的副管线释放掉并提示，需要时再手动预编译一次。
>
> 原因：进世界那一刻主管线往往还没构造出来，自动构建的管线会踩到 Iris 的全局材质状态，
> 表现为“实体渲染不出来”；游戏中由玩家触发时不存在这个时间窗。详见
> [`19-排查记录-进世界预编译与手动预编译的差异.md`](19-排查记录-进世界预编译与手动预编译的差异.md)。

> 历史字段说明：`fixLegacyKeywords`（兼容 GLSL 4.x 保留字）与 `screenshotHoldFrames`
> （截图层数）在 **0.1.9 已删除**，配置文件里留着也无害（Gson 会忽略未知字段）。
> 前者删除的理由见 [`05-排查记录-副管线创建失败.md`](05-排查记录-副管线创建失败.md) 末尾。
> `prewarmPolicy`（0.1.17 的「预编译调度」）在 **0.2** 因语义改变改名为 `remeshPolicy`，
> 旧字段名不再读入。另外「超时回落」（`ScreenshotCapture` 里的 `SETTLE_FALLBACK_MILLIS` /
> `HARD_TIMEOUT_MILLIS`，是代码常量而非配置项）在 0.2 已整体删除，理由见
> [`17-…`](17-功能-截图副管线性能调度与截图进度.md)。
> **0.2.2 又删了三个字段**：`mode`（渲染模式）、`intervalFrames`（帧间隔）、
> `skipWhenScreenOpen`（开界面时暂停副渲染）——只保留“编译好、资源就绪、平时不渲染”
> 这一种行为。旧配置里留着它们无害（读进来被忽略，下次保存自动消失）。
> `screenshotLongEdge`（0.2.2 的“目标长边”）在 **0.2.3** 换成了 `screenshotWidth` /
> `screenshotHeight` 两个字段（宽高各填一个，也可以只填一边让另一边按窗口比例推出）。
> 0.2.3 曾把“像素总量上限”做成硬限制，**0.2.4 改成只警告**（超量渲染是玩家的选择）。

## 性能建议

* 0.2.2 起副管线**平时不渲染**（只保持编译好、资源就绪），所以不做副管线截图时
  它不产生 GPU 开销；切换（F7）依然接近瞬时。
* 常驻的代价是**显存**：副管线的渲染目标、阴影贴图与全部程序都占一份。
  显存紧张时优先降低光影包的阴影分辨率/目标分辨率，或直接减少两个包同时驻留的场合。
* 截图分辨率（`screenshotLongEdge`）是另一处显存开销：4K 档位时副管线的渲染目标
  会按目标尺寸重建，核显建议先用 1920~2560。

## 快捷键

按键注册在 `key.categories.shaderflash` 分类下，可在“选项 → 控制”里改：`swap`（默认 F7）、
`toggle`（F6）、`screen`（F8）。翻译键分别是 `key.shaderflash.swap` / `key.shaderflash.toggle` /
`key.shaderflash.screen`。
