# 排查记录：副渲染擦掉主画面 & 切换后像没开光影（1.1.0 → 1.2.0）

> 说明：本文标题与正文里的 `1.x` 是**开发期间的临时迭代号**，对外版本号为 **0.1**（见 [`../CHANGELOG.md`](../CHANGELOG.md)）。

## 现象

1. 渲染模式 = **每帧**：屏幕上只剩天空/背景色，看不到任何东西。
2. 渲染模式 = **2 帧一次**：画面与纯色背景高频交替闪烁。
3. 用本模组把副光影包（日志里的 C = `CyanideShaders_v1.1`）切为主光影后，
   画面像完全没开光影。

日志本身没有异常：副管线预编译成功（802 ms / 2944 ms）、切换成功（2~31 ms）、没有报错。

## 定位 1：幽灵那一遍把主画面擦掉了

### 原因

原版世界渲染在真正画东西之前会调用一次
`RenderSystem.clear(IZ)`（在 `WorldRenderer.render` 里，Yarn 侧就是
`method_22710` 方法体内的那次 clear），而 **`RenderSystem.clear` 清的是“当前绑定”的帧缓冲**。

Iris 的 `MixinLevelRenderer.iris$beginLevelRender` 恰恰注入在**这次 clear 之后**：

```java
private static final String CLEAR = "Lcom/mojang/blaze3d/systems/RenderSystem;clear(IZ)V";

@Inject(method = "renderLevel", at = @At(value = "INVOKE", target = CLEAR, shift = At.Shift.AFTER, remap = false))
private void iris$beginLevelRender(...) {
    pipeline.beginLevelRendering();     // ← 这里才把渲染目标切到管线的目标/主帧缓冲
    ...
}
```

而上一遍主渲染结束时，绑定着的是**主帧缓冲的颜色附件**（Iris 的 final pass 把成品写进主颜色纹理）。
于是幽灵那一遍的 clear 落在了主帧缓冲上：

* **每帧模式**：每一帧都在画完之后被擦一次 → 屏幕上只剩背景/天空色；
* **2 帧一次**：擦与不擦交替 → 画面与纯色高频闪烁。

### 修法

幽灵那一遍**开始前先换绑**，结束后**还回去**：

```java
GhostFramebuffer.arm();
ghostTarget.beginWrite(true);          // ← 让这一遍里所有 clear/绘制都落在离屏 FBO 上
renderer.renderWorld(tickDelta, limitTime, matrices);
...
finally {
    GhostFramebuffer.disarm();
    ... 还原管线 / 剔除开关 / 视锥体 ...
    realTarget.beginWrite(true);       // ← 把绘制目标还回主帧缓冲（否则 HUD 会被画进幽灵 FBO）
    ShadowRenderer.ACTIVE = false;     // ← 防御性复位（见下）
}
```

顺带加了一道保险：`ShadowRenderer.ACTIVE` 是**全局静态**标志（`ShadowRenderingState.areShadowsCurrentlyBeingRendered()`
就是读它）。它若因异常残留为 `true`，Iris 的 Sodium 兼容层会把区块可见性列表切到“阴影用”的那一份，
主渲染的地形会整片消失。现在幽灵那一遍结束后无条件复位。

## 定位 2：切换主副之后“像没开光影”

这里有两个真实缺陷 + 一个需要说清楚的预期行为。

### 2.1 材质表没有重建（真缺陷）

Iris 只在 **“这个维度还没有管线”** 的分支里消费 `WorldRenderingSettings.reloadRequired`：

```java
public WorldRenderingPipeline preparePipeline(NamespacedId dim) {
    if (!pipelinesPerDimension.containsKey(dim)) {
        pipeline = pipelineFactory.apply(dim);
        pipelinesPerDimension.put(dim, pipeline);
        if (WorldRenderingSettings.INSTANCE.isReloadRequired()) {
            Minecraft.getInstance().levelRenderer.allChanged();   // ← 只有新建管线才走这里
            WorldRenderingSettings.INSTANCE.clearReloadRequired();
        }
    } else {
        pipeline = pipelinesPerDimension.get(dim);                 // ← 我们是走这条
    }
    return pipeline;
}
```

本模组是**把已经建好的副管线塞进这张映射表**，所以那个分支永远不走，
`reloadRequired` 会一直挂着、**区块网格永远不会按新包的材质表/顶点格式重建**，
地形里的材质 ID 就与着色器对不上。

修法：切换时自己判断并消费这个标志 —— 真的变了就调用 `WorldRenderer.reload()`
（即 Iris 自己那条 `allChanged()` 路径）并清掉标志。

### 2.2 写进 Iris 配置的文件名不对（真缺陷）

Iris 的 `iris.properties` 里存的是 shaderpacks 目录下的**真实条目名**（例如 `MakeUp-UltraFast-9.1e.zip`），
而本模组写的是去掉 `.zip` 的名字。当时不影响运行（管线是现成的），但**重启游戏或按 R 重载**时
Iris 会按这个名字找不到包。现在写的是真实条目名。

### 2.3 `CyanideShaders_v1.1` 本来就是一个极简包（预期行为）

这个包整包 18 KB，`shaders/` 里只有：

```
final.fsh / final.vsh
gbuffers_clouds / gbuffers_skytextured / gbuffers_textured
block.properties
```

**没有 `gbuffers_terrain`、没有 `gbuffers_entities`、没有阴影/水面程序。** 也就是说，
它当主光影时地形与实体本来就由 Iris 的 fallback（接近原版）着色器渲染 ——
“裸方块模型 + 原版亮度”是它的正常表现，并不是切换失效。它真正的效果体现在天空、云和 final 调色上。

为了以后能一眼确认这件事，1.2.0 在设置界面的“兼容性自检”里加了一段运行期状态输出：

```
当前管线类：IrisRenderingPipeline，当前包：CyanideShaders_v1.1.zip
shouldOverrideShaders=true（= 正在渲染世界 && 主帧缓冲已绑定），Iris 全局阴影标志 ACTIVE=false
该包自带程序：TERRAIN_SOLID=无 ENTITIES_SOLID=无 SKY_BASIC=有 CLOUDS=有 TEXTURED=有 TERRAIN_TRANSLUCENT=无
副管线槽位：MakeUp-UltraFast-9.1e；副渲染已停用=false
```

“该包自带程序”一列直接说明某个包到底有没有地形/实体着色器；
`shouldOverrideShaders` 则说明 Iris 此刻是否真的在接管着色器。
这两行就能把“包本身没有这个程序”和“切换后没生效”两类问题区分开。

## 本轮验证

* 1.2.0 重新构建后，Mixin 目标与注入点校验对 **Iris 1.7.1 / 1.7.2** 依旧全绿
  （见 [`verification/iris-1.7.1.txt`](verification/iris-1.7.1.txt)、
  [`verification/iris-1.7.2.txt`](verification/iris-1.7.2.txt)）。
* 现象 1/2 的结论来自对**真实字节码与 Iris 源码**的比对：确认 `WorldRenderer.render` 里存在
  `RenderSystem.clear(IZ)`，并确认 Iris 绑定渲染目标发生在它之后（`iris$beginLevelRender`
  的注入点就是 `CLEAR + shift AFTER`）。这是“清错目标”的直接证据。
* 现象 3 的两处缺陷同样是读 Iris 源码得出的结论（`preparePipeline` 的分支结构、
  `iris.properties` 的命名约定）。
