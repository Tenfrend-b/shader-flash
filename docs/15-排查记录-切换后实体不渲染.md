# 排查记录：主管线为空包 + 副管线为其它光影，F7 切换后实体不渲染

> 现象（玩家实测）：主管线是**空包**、副管线是别的光影时，按 F7 主副互换后，**实体消失**
> （地形、天空、后处理都正常，日志里没有任何异常）。
>
> 本文只做**源码级**分析：结论全部来自 Iris 1.7.2 的真实字节码 + 本工程源码。
> 文末给出本轮修复、验证方法，以及仍未定论的部分。

## 1. 先把实体这一条路走一遍（Iris 1.7.2 实测）

### 1.1 实体怎么被画出来

1. `WorldRenderer.renderLevel` 的 `"entities"` 段：`entitiesForRendering()` → 逐个
   `WorldRenderer.renderEntity`（intermediary `method_22977`）→ `EntityRenderDispatcher.render(...)`。
   **但这些绘制不是立刻提交的**：它们全部进 `RenderBuffers.bufferSource()`，而 Iris 用
   `MixinRenderBuffers` 把它换成了自己的 `FullyBufferedMultiBufferSource`
   （只要 `RenderBuffers` 的 `begins > 0`，该计数由 `MixinLevelRenderer` 在 `renderLevel`
   的 HEAD/RETURN 增减）。**实体是“先缓冲、后在 translucent 标记处统一 flush”的。**
2. flush 时才真正 `type.setupRenderState()` → `ShaderInstance.apply()` → `glUseProgram`。
   也就是说：**实体用的着色器是在 flush 那一刻从“当前管线”的 `ShaderMap` 里取的**
   （`MixinGameRenderer.override()` → `Iris.getPipelineManager().getPipelineNullable()`）。
3. 另一头，**顶点布局**是在“写顶点”时决定的，与上一步没有任何联系：
   * Sodium 兼容层的 `MixinModelVertex` / `MixinEntityRenderDispatcher`：
     `IrisApi.isShaderPackInUse() && ImmediateState.renderWithExtendedVertexFormat`
     → 为真就写 `EntityVertex`（扩展格式：多出 `mc_Entity` / `midTexCoord` / `tangent` 等）；
   * 普通路径的 `MixinBufferBuilder.iris$extendFormat`：
     `WorldRenderingSettings.shouldUseExtendedVertexFormat()` 决定 BufferBuilder 用不用扩展格式。

### 1.2 关键不变量

> **只要“顶点是扩展格式”，绘制它的着色器就必须是 Iris 自己的程序**
> （光影包的 `gbuffers_entities`，或 Iris 合成的 fallback）。

一旦违反——顶点按扩展格式写、却用**原版**着色器去画——原版程序会按
`DefaultVertexFormat.NEW_ENTITY` 的偏移去读扩展布局的顶点：位置、UV、法线、颜色全部错位，
几何体要么糊成一团，要么直接被算到屏幕外。**玩家看到的就是“实体没了”**；
而地形走 Sodium 自己的区块渲染器、不经过这条链，所以完全正常。这与玩家报告完全吻合。

### 1.3 这条不变量为什么会被破坏

两处判断**不同源**：

| 判断 | 依据 | 性质 |
| --- | --- | --- |
| 写顶点用不用扩展格式 | `IrisApi.isShaderPackInUse()` + `ImmediateState.renderWithExtendedVertexFormat` | 只说“装了光影” |
| 用不用光影包的实体着色器 | `IrisRenderingPipeline.shouldOverrideShaders()` = `isRenderingWorld && isMainBound` | 两个**运行时**标志 |

`MixinGameRenderer` 的写法是 `else if (shouldOverrideShaders()) { override(ShaderKey.ENTITIES_*) }`——
**条件不满足时它不换着色器，直接保留原版**。于是只要在实体 flush 的那一刻
`isRenderingWorld` 或 `isMainBound` 有一个是 false，就会出现“扩展格式顶点 + 原版着色器”的错配。

这两个标志都不是“管线状态”，而是一帧内被反复改写的运行时标志：

* `isRenderingWorld`：`beginLevelRendering()` 置 true，`finalizeLevelRendering()` 置 false；
* `isMainBound`：**任何 `RenderTarget.bindWrite(...)` 都会改写它**——Iris 的
  `MixinRenderTarget`（`state_tracking` 包）在 `bindWrite` 返回时比较
  `this == Minecraft.getInstance().getFramebuffer()`，并写进当前管线的监听器。
  1.20.4 的 `RenderTarget` 字节码里，`clear(boolean)` 会调用 `bindWrite(true)`，
  而收尾的 `unbindWrite()` **不经过 `bindWrite`**：也就是“某个非主渲染目标被 clear”
  会让 `isMainBound` 变成 false，并且不保证有人把它改回来。
  （本机 graphicsMode=Fancy 时 `weatherTarget`/`itemEntityTarget`/`entityTarget` 都是 null，
  这条不一定触发；但足以说明这个标志本身是脆弱的。）

## 2. 本模组在这条链上额外引入的风险（我们要负责的部分）

幽灵渲染就是**在同一帧里把整帧世界渲染再跑一遍**（换管线、换主帧缓冲），于是：

* 所有“单帧内成对出现”的全局状态都被暴露在**双倍**的异常路径风险下；
  0.1.1 / 0.1.2 / 0.1.4 已经为此保存/还原了 `ImmediateState`、`CapturedRenderingState`、
  `ShadowRenderer.ACTIVE`、视锥体、剔除开关、主帧缓冲；
* 但**实体路径上还有两个同类全局没有被管理**：
  1. **`DepthColorStorage` 的“深度/颜色写入锁”**：Iris 对“不是它自己程序”的
     `ShaderInstance.apply()` 会调用 `DepthColorStorage.disableDepthColor()`
     （`colorMask(false,false,false,false)` + `depthMask(false)`），由同一个着色器的 `clear()` 解锁。
     **一旦这对配对被打断，之后所有绘制都不会写出任何像素**——表现就是“画了但看不见”。
     它是静态状态，会跨帧残留。
  2. **`HandRenderer.ACTIVE`**：`MixinGameRenderer` 里实体渲染类型的 getter 写着
     `else if (HandRenderer.INSTANCE.isActive()) → override(HAND_*)`，
     即实体会被当成“手”，用另一套程序与另一套绑定点去画。

两者都只在“幽灵那一遍以异常/半途方式退出”时才会残留，但**一旦残留，症状正好就是实体异常**。

## 3. 本轮修复（0.1.15）

### 3.1 实体着色器安全网（`EntityShaderGuardMixin`，13 个 getter）

在 Iris 那些 `getRendertypeEntity*Shader`（intermediary `method_34502`…`method_34514`、
`method_42595`）的 **RETURN** 处兜底，触发条件全部从严，健康路径下是**空操作**：

1. Iris 这次返回的**不是**它自己的程序（`ExtendedShader` / `FallbackShader`）——说明它没接管；
2. `IrisApi.getInstance().isShaderPackInUse()` 为真（装了光影）；
3. **顶点确实是扩展格式**：`WorldRenderingSettings.INSTANCE.shouldUseExtendedVertexFormat()`
   且 `ImmediateState.renderWithExtendedVertexFormat`；
4. 不在阴影阶段、手部渲染中、方块实体阶段（这三处 Iris 本来就有自己的程序，走不到这里）；
5. 当前管线是 `ShaderRenderingPipeline`，且它的 `ShaderMap` 里有对应的实体程序。

满足时改用当前管线的实体程序，key 与 Iris 自己的映射逐条对齐：
`ENTITIES_SOLID_DIFFUSE` / `ENTITIES_CUTOUT_DIFFUSE` / `ENTITIES_TRANSLUCENT` /
`ENTITIES_EYES_TRANS` / `ENTITIES_CUTOUT` / `ENTITIES_ALPHA`。
**生效时会在日志里打一行 WARN**（5 秒最多一条）——这就是“机制被命中”的直接证据。

### 3.2 幽灵渲染的完整状态屏障

`DuoManager.renderSecondaryPass()` 现在额外保存/还原：

* `DepthColorStorage.isDepthColorLocked()`：幽灵那一遍开始前没锁、结束后却发现锁上了 → 立刻解锁并告警；
* `HandRenderer.ACTIVE`（新增 `HandRendererAccessor`）：不一致就还原并告警。

### 3.3 兼容性自检新增“实体路径”一行

```
实体路径：深度颜色锁=… ，手部渲染中=… ，阴影ACTIVE=… ，扩展顶点格式(全局)=…
```

配合原有的 `shouldOverrideShaders=…`、`ENTITIES_SOLID=…`，足以区分
“实体没用上光影包的程序”“顶点布局错配”“写入被锁住”这几类原因。

### 3.4 校验结果

* `VerifyTool`：**全部通过**——13 个新注入点逐条确认目标方法存在、描述符一致，所有类引用可解析；
* 离线链两个回归测试：`ROTATION TEST PASSED`、`BLOCK ID TEST PASSED`；
* 产物：`outputs/shader-flash-0.1.15.jar`。

## 4. 怎么验证这次修复

1. 把 `shader-flash-0.1.15.jar` 放进 `mods/`（替换 0.1.14）；
2. 进世界 → 主管线选**空包**、副管线选**其它光影** → 按 F7 切换；
3. 观察实体（生物 / 盔甲架 / 掉落物）是否正常；
4. 打开 `logs/latest.log` 搜 `ShaderFlash`：
   * 出现 `实体着色器安全网生效：…` → **命中的就是 1.3 的机制**，安全网已经把它兜住；
   * 没出现、实体也正常 → 修复以另一种方式生效（状态屏障），同样可以接受；
   * 没出现但实体仍然消失 → 说明是**另一类机制**（不是“原版着色器读扩展顶点”），
     请把游戏内「兼容性自检」的两行（`渲染时的真实状态` / `实体路径`）连同 `latest.log` 一起发我。

## 5. 还没有定论的部分（如实说明）

* **“那一帧为什么会让 `isMainBound`/`isRenderingWorld` 落到 false”没有实机证据**。
  本文能证明的是：这个不变量一旦被破坏，症状必然就是实体消失；
  而本模组的两条额外路径（幽灵渲染 / 主副互换）会让这些运行时标志暴露在双倍风险下。
  具体是哪条路径踩中的，需要第 4 步那行 WARN 或自检输出来闭环。
* 本轮**没有**真机复现（环境与侵入性考虑），因此“安全网是否命中”要由下一次实测确认。
* `GbufferPrograms` 的三个静态标志（`entities`/`blockEntities`/`outline`）也是同类全局，
  但它们失衡时会**立刻抛异常**（自证），所以本轮没有额外加屏障；
  若日志里出现 `GbufferPrograms in weird state`，按本文同一思路补即可。
