0.1.4 处理的三件事，以及各自的证据。

## 一、“由近到远的缓慢重载过程”是投递优先级造成的

### 证据

Sodium 的构建队列（`me.jellysquid.mods.sodium.client.render.chunk.compile.executor.ChunkJobQueue`）：

```java
public void add(ChunkJob job, boolean important) {
    Validate.isTrue(this.isRunning(), "Queue is no longer running");

    if (important) {
        this.jobs.addFirst(job);      // ← 插到队首
    } else {
        this.jobs.addLast(job);       // ← 排到队尾
    }

    this.semaphore.release(1);
}
```

再看 `RenderSectionManager.scheduleRebuild(...)`：

```java
if (allowImportantRebuilds() && (important || this.shouldPrioritizeRebuild(section))) {
    pendingUpdate = ChunkUpdateType.IMPORTANT_REBUILD;
} else {
    pendingUpdate = ChunkUpdateType.REBUILD;
}
```

其中 `shouldPrioritizeRebuild` 只对**距相机 16 格以内**的区块返回 true。

本模组此前调用的是：

```java
renderer.scheduleRebuildForChunks(minX, minY, minZ, maxX, maxY, maxZ, false);   // important = false
```

于是：

* 全部任务都是 `REBUILD`（只有玩家身边 16 格内的会自动升级）；
* 全部 `addLast` 排到队尾，跟正常区块加载、方块更新等任务抢不到优先权。

几万个任务这样慢慢往前挪，就是玩家看到的“明显的从近到远的重载过程”。

### 修法

```java
// 按“由远到近”投递；important 队列是 addFirst（后进先出），
// 所以最终执行顺序是“由近到远”，玩家脚下先补齐。
columns.sort((a, b) -> Long.compare(b[2], a[2]));
for (...) renderer.scheduleRebuildForChunk(chunkX, y, chunkZ, true);   // important = true
```

## 二、副管线截图拍到“半成品地形”

切换刚触发过一次区块重建时按 F2，Sodium 的构建队列里还压着几万个任务，
于是拍到的是「一半旧材质、一半新材质」。

### 修法

Sodium 提供了现成的“重建是否做完”的判断：

```java
public boolean isTerrainRenderComplete() {
    return this.renderSectionManager.getBuilder().isBuildQueueEmpty();
}
```

`ScreenshotCapture` 现在会：如果最近 60 秒内触发过重建、且队列未空，
就保持副管线的画面继续等（不拍），直到队列清空再拍；上限 60 秒，
超时会提示并按当前画面拍。等待期间聊天框会先给出提示。

> **0.2 更新**：这里说的“60 秒上限、超时就按当前画面拍”已经删除 —— 有了截图进度条之后，
> 玩家能看见还在重建/预热，超时回落只会拍到半成品。现在没稳定就一直等，
> 只保留“连续 100 tick 没有渲染帧（暂停/最小化）就取消”的保护。
> （0.2.1 起这个阈值成了可调项：设置界面「最大静默等待时间」，100 ~ 32767 tick。）

## 三、实体花斑：先隔离我们这个模组会污染的状态

### 已排除的部分

逐个核对过 Iris 1.7.2 的实体渲染路径，以下**都不存在“按包缓存”的问题**，
每次都是现取现用：

| 状态 | 取值处 | 结论 |
| --- | --- | --- |
| `entityId`（实体材质掩码来源） | `MixinEntityRenderDispatcher.iris$beginEntityRender` → `WorldRenderingSettings.getEntityIds()` | 每次绘制现取 ✓ |
| `blockEntityId` | `MixinBlockEntityRenderDispatcher` → `getBlockStateIds()` | 每次绘制现取 ✓ |
| `currentRenderedItemId` | `MixinItemRenderer` / 各盔甲层 → `getItemIds()` / `getBlockStateIds()` | 每次绘制现取 ✓ |
| 实体用的着色器程序 | `GameRendererMixin` 的 `getRendertype*Shader` 注入 → 当前管线的 `ShaderMap` | 每次绘制现取 ✓ |
| 顶点格式 | `MixinBufferBuilder` / `MixinVertexFormat` → `shouldUseExtendedVertexFormat()` | 全局开关，两条管线都为 true ✓ |

另外确认了 Photon 侧：`EntityPatcher` 把 `entityId`/`blockEntityId`/`currentRenderedItemId`
替换成逐顶点属性 `iris_Entity`（`flat out ivec3`），值来自顶点数据，
而顶点数据写入时读的正是上面那些“每次绘制现取”的值。

### 仍然可疑的一处：全局即时状态泄漏

`ImmediateState` 的两个静态标志决定顶点缓冲按哪套布局建立与绑定：

```java
public class ImmediateState {
    public static boolean isRenderingLevel = false;
    public static boolean usingTessellation = false;
    public static boolean renderWithExtendedVertexFormat = true;   // ← 布局开关
}
```

`MixinBufferSource` 在**非世界渲染**的 `endBatch` 前后把它设成 `false` / 再设回 `true`：

```java
@Inject(method = "endBatch(...)", at = @At(..., target = "RenderType;end"))
private void iris$beforeFlushBuffer(...) { if (iris$notRenderingLevel()) ImmediateState.renderWithExtendedVertexFormat = false; }

@Inject(method = "endBatch(...)", at = @At(..., shift = At.Shift.AFTER))
private void iris$afterFlushBuffer(...) { if (iris$notRenderingLevel()) ImmediateState.renderWithExtendedVertexFormat = true; }
```

这是一对**必须成对执行**的注入：只要中间的 `RenderType.end(...)` 抛一次异常，
标志就会停在 `false`，之后所有“按扩展格式建立的顶点缓冲”都会被按普通布局绑定
—— 属性错位，表现正是**表面出现杂色/花斑**。

本模组每个渲染帧都会额外跑一整遍世界渲染（幽灵那一遍，用另一条管线），
把这类“单帧内成对”的状态暴露在双倍的风险下。

### 修法

幽灵渲染前后显式保存/还原：

```java
boolean previousRenderLevel = ImmediateState.isRenderingLevel;
boolean previousExtendedFormat = ImmediateState.renderWithExtendedVertexFormat;
int previousEntityId = CapturedRenderingState.INSTANCE.getCurrentRenderedEntity();
int previousBlockEntityId = CapturedRenderingState.INSTANCE.getCurrentRenderedBlockEntity();
int previousItemId = CapturedRenderingState.INSTANCE.getCurrentRenderedItem();
...
// finally:
ImmediateState.isRenderingLevel = previousRenderLevel;
ImmediateState.renderWithExtendedVertexFormat = previousExtendedFormat;
CapturedRenderingState.INSTANCE.setCurrentEntity(previousEntityId);
CapturedRenderingState.INSTANCE.setCurrentBlockEntity(previousBlockEntityId);
CapturedRenderingState.INSTANCE.setCurrentRenderedItem(previousItemId);
```

这样幽灵那一遍**无论怎么退出**（包括异常路径）都不会把状态留给主画面。

### 如果花斑还在

自检现在会打印采样到的即时状态。请按 F8 → 「兼容性自检」，
把这几行发我：

```
渲染时的真实状态：…；shouldOverrideShaders=…，ENTITIES_SOLID=…（ExtendedShader / FallbackShader）
  即时状态：isRenderingLevel=…，renderWithExtendedVertexFormat=…，entityId=…，blockEntityId=…，itemId=…
```

* 如果 `ENTITIES_SOLID` 是 `FallbackShader` → 说明实体压根没用上光影包的着色器（换管线时程序没被正确选中）；
* 如果 `renderWithExtendedVertexFormat=false` 或 `isRenderingLevel` 异常 → 就是上面那种布局错配；
* 如果两者都正常 → 说明是 Photon 内部（材质/光照）的问题，我再往那边查。

加上一张出问题时的截图（能看出是“像马赛克一样的属性错位”还是“材质/光照偏色”），就能直接定性。
