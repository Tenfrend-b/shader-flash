# 排查记录（已定案）：预编译出来的副管线里，部分着色器程序**链接失败**

> 现象（玩家实测，0.1.15，Intel Iris Xe + Fabric 0.19.5 + Iris 1.7.2）：
> **按 F7 主副互换后「手部 + 实体」同时消失**（地形、天空、后处理都在），
> 同一个主副组合会 **✓✗✓✗ 交替**，**按 R 让 Iris 重载必然恢复**。

## 1. 定案证据（logs/latest.log，11:44–11:50）

### 1.1 驱动直接报出链接失败

```
[11:44:41] [ShaderFlash] 开始预编译副管线 iterationT 3.2.0（后台）
[11:44:42] OpenGL debug message: id=1, source=SHADER COMPILER, type=ERROR, severity=HIGH,
           message='SHADER_ID_LINK error has been generated. GLSL link failed for program 261, "":
             The shader uses varying iris_entityInfo, but previous shader does not write to it.
             The shader uses varying v_texCoord, but previous shader does not write to it.
             The shader uses varying v_color, but previous shader does not write to it.
             Out of resource error.'
[11:44:42] [Render thread/WARN]: Error encountered when linking program containing VS sky_textured and FS sky_textured.
[11:44:42] OpenGL debug message: id=1282, source=API, type=ERROR, severity=HIGH,
           message='Error has been generated. GL error GL_INVALID_OPERATION in (null):
             (ID: 3891749976) glGetUniformLocation- program 261, "" is not linked'
```

* **`Out of resource error`** = 驱动资源不足（这里是 Intel 核显；一次要同时驻留
  两条完整管线的程序，`iterationT` 这种大包尤其容易顶到上限）；
* 链接失败的程序按原样留在管线的 `ShaderMap` 里，**Iris 与原版都只打一条 WARN 就继续**；
* 用未链接的程序绘制 → `glGetUniformLocation` 报 `is not linked`、**绘制本身不输出任何像素**；
* 玩家看到的就是：**该管线的程序负责的那些东西全部消失**。
  本机实测缺的是 `sky_textured` 以及随后的 3 个程序（程序号 261/264/270/273），
  玩家报的现象是「手部 + 实体」消失——同一类失败的不同程序组合。

### 1.2 为什么表现成「同一个组合 ✓✗✓✗ 交替」

坏掉的是**某一个管线实例**（那条预编译出来的），不是"某个组合"：

| 操作 | 主位上的实例 | 结果 |
| --- | --- | --- |
| 空包（Iris 自己编译、链接成功）当主 | 好的实例 | ✓ 正常 |
| F7 → 把**预编译**出来的那条换到主位 | 坏的实例 | ✗ 手部/实体消失 |
| 再 F7 → 换回来 | 好实例 | ✓ 恢复 |
| 再 F7 → 换过去 | **还是那个坏实例** | ✗ 又消失 |

日志里 11:47:34 ✓ / 11:47:54 ✗ / 11:48:12 ✓ / 11:48:28 ✗（同一组合）完全吻合。
按 R 会让 Iris **销毁并重新编译**所有管线 → 链接成功的新实例 → 必然恢复 ✓。

### 1.3 与「预编译时是否补建阴影渲染目标」的相关性（同一根因的两个表现）

| 时间 | 预编译时的日志 | 之后被提升时的表现 |
| --- | --- | --- |
| 11:29:03 | `阴影渲染目标：缺失` → **`已补建阴影渲染目标`** | 11:30:53 / 11:31:20 **✗ 无法渲染** |
| 11:31:46 | `阴影渲染目标：已就位` | 11:33:09 **✓ 可以渲染** |

两条线索指向同一件事：**预编译那一刻驱动资源是否够用**。
资源不够时，链接失败（并在构造之后才需要补建的阴影目标，也正是“构造期就缺资源”的旁证）；
资源够时一切正常。这解释了为什么之前各种「换包 / 换顺序 / 换维度」都能改变结果。

## 2. 修复（0.1.16）

### 2.1 新增管线健康检查（`PipelineHealth` + `ShaderProgramAccessor`）

* `ShaderProgramAccessor` 打开 `ShaderProgram.glRef`（intermediary `field_29493`），
  拿到 GL 程序号；
* `PipelineHealth.findUnlinkedPrograms(pipeline)` 遍历该管线 `ShaderMap` 的每个非 null 程序
  （null = 没有阴影贴图时的阴影 key，属正常），查 `GL_LINK_STATUS`，返回未链接的 `ShaderKey` 名。

### 2.2 预编译：不健康就释放重试一次，仍不健康就明确失败

`DuoManager.compilePrewarm` 在构造 + 补建阴影目标之后立刻检查：

1. 不健康 → `pipeline.destroy()` 释放掉这次占用的资源 → 下一 tick 重来一次
   （第一次尝试自己的程序也占资源，释放后再试往往就够用了）；
2. 仍然不健康 → **放弃这条管线**，日志与聊天框明确说明：
   「副管线 X 有 N 个程序没能链接成功（驱动资源不足），已放弃这条管线」+ 解决建议。

**关键点：坏管线绝不会被交给玩家当主/副管线。**

### 2.3 切换前再检查一次（防御）

`DuoManager.swapPrimary` 在提升之前复查 `GL_LINK_STATUS`：
不健康就**拒绝提升**并给出同样的说明（`PackSlot.unhealthyPrograms` 记录结论）。
这样即使管线是在预编译之后才变坏的，也不会出现「切过去手部/实体集体消失」。

### 2.4 兼容性自检新增一行

```
程序链接：主管线=全部已链接 ，副管线=全部已链接
```

异常时直接列出未链接的 `ShaderKey` 名（例如 `SKY_BASIC、ENTITIES_SOLID`）。

## 3. 怎么验证

1. 用 0.1.16 进世界，主管线随便选、副管线选 `iterationT 3.2.0`（最容易复现的包）；
2. 等预编译结束：
   * 若日志出现 `有 N 个程序没有链接成功（…）——这是驱动资源不足的典型表现，正在释放并重试一次`
     且随后 `副管线 X 预编译完成` → 重试成功，F7 切过去应当**手部与实体正常**；
   * 若直接出现 `副管线 X 的程序链接失败（…），放弃这条管线` → 模组已经拒绝使用它，
     **当前主画面不会因此变坏**（这就是本次修复要保证的）；
3. 不论哪种情况，按 F7 都不应该再出现「手部/实体消失」。若仍出现，请把
   「兼容性自检」里 `程序链接` 那一行连同 `latest.log` 发我。

## 4. 已知代价与后续可做的事（如实说明）

* **根因在驱动资源上限**，本模组只能“检测 + 拒绝 + 提示”，不能凭空变出显存/程序槽位。
  核显 + 两条大管线的组合本来就容易触顶；玩家侧最有效的做法是：
  用更轻的副包、或先按 R 重载释放资源再试。（0.2.2 起副管线平时不渲染，
  已经比当时的“每帧模式”省下不少资源；模式开关本身已删除。）
* 0.1.15 的「实体着色器安全网」仍然保留：它针对的是另一类错配
  （顶点扩展格式 + 原版着色器），与本次链接失败无关，两者互补。
* 还没有做（超出本次范围）：**在链接失败时自动降级**（例如只预编译主包程序、
  副管线按需懒编译），那需要 fork Iris 的管线构造过程。
