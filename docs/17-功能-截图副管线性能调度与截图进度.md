# 功能：「截图副管线性能调度」（五档）+ 截图进度提示

对外版本：**0.2**。两件事都来自玩家实测反馈。

## 一、先说结论：这个设置**只影响截图**，别再扩权

**0.1.17 想做的事（把“后台预编译”改成五档调度）是错的**，0.2 已经回退，理由如下：

| 阶段 | 能不能挪出渲染线程 | 能不能“调度” |
| --- | --- | --- |
| 解包（zip → `config/shaderflash/packcache/`） | **能**（已在工作线程） | 是（本来就是后台） |
| 解析（`new ShaderPack(...)`） | **不能**：Iris 解析 `shaders.properties` 时会做 GL 查询 | **不能**：一步到底的原子操作 |
| 编译（`new IrisRenderingPipeline(...)`） | **不能**：构造函数里直接调 GL 编译链接全部程序 | **不能**：同上 |

解析与编译既然**无法分解**，围着它们做“什么时候做/拆到两个 tick”的菜单就是**名不副实**：
玩家选了档位，实际感知到的仍然是一段无法回避的卡顿。所以 0.2 把这几段代码**整体删除**，
设置项改名并**严格限定作用域**：

> **「截图副管线性能调度」只决定：副管线截图取景前那一轮“切到副包材质”的区块重建，
> 每 tick 往 Sodium 投递多少区块段。**

明确**不受影响**的两条路径（0.2 起一次性投完，和这项设置无关）：

* **F7 主副互换**：交换后新主管线的区块更新速度必须最快，不能因为一个截图相关的设置变慢；
* **截图结束后的材质还原**：拍完就要把地形变回主管线的材质，玩家马上要看结果。

（预编译的**解包**仍然在工作线程上跑，线程优先级是最低的；这条从 0.1.9 起就有，与本次改动无关。）

## 二、五档策略（只影响投递节奏）

设置界面「副管线」一节里的 **截图副管线性能调度**（默认 **中负载**）：

| 档位 | 每 tick 投递的区块段数 | 前台表现 |
| --- | --- | --- |
| **极低负载**（minimal load） | 300 | 最稳，地形替换最慢 |
| **低负载**（low load） | 700 | 稳 |
| **中负载**（medium load，默认） | 1500 | 折中 |
| **高负载**（high load） | 4000 | 略快，可能有一次小尖峰 |
| **最大负载**（max load） | 一次性全部 | 与不带分批时相同，尖峰最明显 |

* 总工作量不变，只是把“一次性把十几万段排进队列”摊成多个 tick；
* 依旧“旧网格渲染到新网格建好”（无可见卸载），所以慢的只是**替换完成的时间**，
  不是画面质量；
* 截图流程会**一边投递一边显示进度**（见下一节），慢档位下玩家能清楚看到还要多久。

## 三、副管线截图的进度提示

按 F2 之后，HUD（需要打开 `HUD 状态` 开关）会在状态行下面显示本次取景的进度：

```
[双管线] 副管线截图（MakeUp-UltraFast-9.5e）：正在按副包材质重建地形
         区块段 45,231 / 114,264（39%）
         [##########                    ]
         预热 0 / 20 帧 · 已等待 3.4 s
```

* 三个阶段会依次显示：**正在按副包材质重建地形 → 正在预热副管线画面 → 即将按快门**；
* 区块段进度来自 Sodium 的构建队列（`rebuildLists` 登记数 + 队列 + 忙碌线程），
  阶梯是“已投递 + 在跑 + 还在排队”，所以是**估算**；拿不到队列信息时显示
  `区块段统计不可用，等待重建完成…`（换 Sodium 版本时不会因此出错）；
* 「预热 x / y 帧」来自本模组自己的取景流程，见下面第四节。

## 四、「概率黑屏」的正确解释（玩家实测结论）

旧文档（`docs/03`）把“副管线截图偶发纯黑”记成一个未定论的已知问题。
**0.1.16 实测后定案：与模组的工作原理无关**——MakeUp（MFU）这类包**刚加载时整屏极暗**，
要**继续渲染 10~20 帧**，等它自己的“人眼适应”把亮度抬起来，画面才可用。
这只是光影包自己的显示策略，模组只是“拍得太早”。

对应改动：新增 `取景预热帧数`（默认 **20**，设置界面 0~60 可调，步进档位
`0/4/8/10/12/16/20/30/40/60`），取景前先让副管线连续渲染这么多帧再按快门。
每次按 F2 都从头预热一次（光影包的适应是按渲染时序自己爬的）。

## 五、删掉的「超时回落」（0.2）

旧版截图流程有一条“等太久就按当前画面拍”的兜底（`SETTLE_FALLBACK_MILLIS = 12 s`、
`HARD_TIMEOUT_MILLIS = 60 s`），拍到的往往是半成品地形。
**既然现在有进度条，玩家能看见“还在重建/还在预热”，这条兜底就没有意义了**，
0.2 把这两个常量、对应分支、以及 `screenshot_terrain_timeout` 文案一起删除：

* 地形重建没稳定 → **一直等**（不再有“等不及就拍一张”）；
* 唯一保留的收尾是：连续若干 tick **一帧都没渲染出来**（窗口最小化 / 渲染卡死）时取消本次截图。
  这不是回落，而是收尾——否则 F2 会永远卡在等待状态，之后再也截图不了。

## 六、最大静默等待时间（0.2.1 起可调）

上面那条收尾原本写死 100 tick（≈5 秒）。实测调试时它太容易触发（切窗口、暂停游戏、加载卡住
都会被算作“没有渲染帧”），于是 0.2.1 把它做成设置界面「副管线截图」一节里的可调项
**「最大静默等待时间」**（左键 +1 档、右键 -1 档）：

| 档位 | 100 / 200 / 400 / 600 / 1000 / 2000 / 4000 / 8000 / 12000 / 16384 / 24000 / 32767 tick |
| --- | --- |
| 折算 | ≈5 秒 ~ ≈27 分钟（20 tick = 1 秒） |

* 配置字段 `noFrameTimeoutTicks`，越界值会被夹回 `100 ~ 32767`（手工改 JSON 也安全）；
* **它只决定“收尾”什么时候发生**，与取景时机、超时回落都无关：只要还在出帧，
  就仍然一直等到地形重建稳定为止；
* 触发时日志会写明当时的计数与阈值：
  `连续 N tick 没有任何渲染帧（阈值 M tick），已取消`。

## 七、怎么验证

1. **作用域**：把档位调到 **极低负载**，然后按 F7 互换主副 ——
   日志里应当是 `已把 N 个区块段排队后台重建（无可见卸载）`（**没有**“分批”字样），
   地形替换速度与档位无关；
2. **截图**：同样的档位下按 F2 —— 日志里应当是
   `副管线截图：切到副包材质（…）：已把 N 个区块段按「极低负载」分批排队重建`，
   并且 HUD 进度条推进得明显更慢、更平稳（对照组：把档位调到「最大负载」，应一次性投完）；
3. **截图进度**：打开 `HUD 状态` 与 `副管线截图`，把副包设成 MFU，按 F2：
   HUD 应先显示地形重建进度条（区块段计数与百分比随之增长），
   然后进入 `正在预热副管线画面` 并显示 `预热 x / 20 帧`，最后 `即将按快门` 并存盘；
   得到的 PNG 不应再是那张偏黑的画面。
4. **无渲染帧阈值**：调到 **32767** 后按 F2 并立刻把窗口最小化（或暂停游戏）很久 ——
   本次等待**不该**被取消；调回 **100** 再重复一次，应看到
   `连续 N tick 没有任何渲染帧（阈值 100 tick），已取消`。
