# 原理与实现

## 1. Iris 的一条管线是什么

Iris 1.7.x 里，一条“渲染管线”就是 `net.irisshaders.iris.pipeline.IrisRenderingPipeline`
的一个实例。它的构造函数长这样（1.7.1 反编译确认）：

```java
public IrisRenderingPipeline(ProgramSet programSet)
```

它把一整套东西都装在自己身上：全部着色器程序（`ShaderMap`）、自己的渲染目标
（`RenderTargets`）、阴影贴图（`ShadowRenderTargets`）、composite / deferred / final pass
渲染器、自定义贴图、Sodium 地形管线……也就是说，**一个实例 === 一条完整管线**。

每帧的生命周期由 Iris 自己的 mixin 驱动：

| 时刻 | Iris 的动作 |
| --- | --- |
| `WorldRenderer.render` HEAD | `pipeline = Iris.getPipelineManager().preparePipeline(getCurrentDimension())` |
| 清屏之后 | `pipeline.beginLevelRendering()` |
| 渲染天空之前 | `pipeline.renderShadows(...)` |
| `WorldRenderer.render` 返回前 | `pipeline.finalizeLevelRendering()` → composite + final pass（写主帧缓冲） |
| `GameRenderer.renderWorld` 返回后 | `pipeline.finalizeGameRendering()`（色彩空间转换） |
| 切换光影包 / 换维度 | `PipelineManager.destroyPipeline()` → 全部销毁重建 |

关键点：**每一处取管线，都是问 `Iris.getPipelineManager()`**。这就是本模组的着力点。

## 2. 第二条管线是怎么来的

Iris 自己创建管线的私有方法 `Iris.createPipeline(NamespacedId)`，去掉错误处理之后就是：

```java
ProgramSet programSet = currentPack.getProgramSet(dimensionId);
return new IrisRenderingPipeline(programSet);
```

本模组照做一遍，只不过用的是第二个光影包：

```java
ShaderPack pack = new ShaderPack(packRoot, options, StandardMacros.createStandardEnvironmentDefines());
ProgramSet programSet = pack.getProgramSet(dimension);
WorldRenderingPipeline ghost = new IrisRenderingPipeline(programSet);
```

构造完成的那一刻，第二条管线的着色器已经全部编译、显存已经全部分配好，这就是
“同时加载两套渲染管线”。之后它一直驻留，直到玩家关掉双管线、换世界或 Iris 重载。

几个必须照抄 Iris 的细节：

* **选项**：读 `shaderpacks/<包名>.txt`（玩家在光影设置里改过的值）+ Iris 的选项队列，
  否则副管线会用默认参数，和主画面就不是“同样的画面”了；
* **zip 包**：Iris 自己的 zip 文件系统在它重载时会被关掉，副管线必须自己复制一份 zip
  到 `config/shaderflash/packcache/` 再打开（顺便避免“主副是同一个包”时两次打开同一 zip）；
* **维度**：`ProgramSet` 是按维度取的，换维度后副管线需要重建。

## 3. 副管线那一遍离屏渲染

挂在 `GameRenderer.renderWorld(float, long, MatrixStack)`（intermediary `method_3188`）上：

* **尾部（TAIL）**：新管线建好之后补渲染一帧（0.2.2 起只在这一次触发；以前是“每帧 / 每 N 帧”），
  这时主画面已经画完，输出进离屏目标，玩家看不到；
* **入口（HEAD）**：`DuoManager.captureSecondaryFrame()` —— 「副管线截图」的取景，
  输出到主帧缓冲（跟随窗口）或目标尺寸的离屏目标（高清档位），随后立刻读像素。

> 尾部那一帧由调试开关 `initialWarmupRender` 控制（0.2.5 新增，默认开）。
> 关掉即“零帧就绪”：省掉一整遍世界渲染，但要承担“第一次切换时 F7 的第一帧可能是黑的 /
> 现编译地形程序”的代价 —— 出事把开关打回去即可，不需要换版本。
> 另外，副管线构造时就已经把 Iris 的 `initializedBlockIds` 标记成 true（见
> `IrisRenderingPipelineAccessor`），所以它的第一次 `beginLevelRendering()` 不会触发
> `allChanged()` 全区重建 —— 关掉这一帧不会带来整世界重载。

> **0.1.1 修正**：`renderWorld` 会直接改写调用方传进来的那个 `PoseStack`
> （方法中段对同一个栈做 `mulPose(相机 pitch)` 与 `mulPose(相机 yaw + 180)`，
> 且方法内没有配对的 push/pop——原版靠调用方每帧 `new PoseStack()` 来丢弃它）。
> 所以尾部复用同一个栈之前**必须先把它还原**：现在的做法是在 `method_3188` 的 HEAD
> 做一次 `matrices.push()`，在 TAIL 调用副渲染**之前** `matrices.pop()`。
> 否则副管线那一遍的相机旋转会被叠加两次，视角与主管线完全不同（见
> [`09-修复记录-0.1.1.md`](09-修复记录-0.1.1.md) ①，含数值验证）。

这一遍的全部动作：

```java
// 1) 记下现状
Map<NamespacedId, WorldRenderingPipeline> pipelines = ((PipelineManagerAccessor) pm).shaderflash$getPipelinesPerDimension();
WorldRenderingPipeline previous = pipelines.get(dim);
boolean previousCulling = client.chunkCullingEnabled;
Frustum previousFrustum = ((WorldRendererAccessor) client.worldRenderer).shaderflash$getFrustum();

// 2) 把“当前管线”换成副管线
pipelines.put(dim, ghost.pipeline);
((PipelineManagerAccessor) pm).shaderflash$setPipeline(ghost.pipeline);
client.chunkCullingEnabled = !ghost.pipeline.shouldDisableOcclusionCulling();

// 3) 把“主帧缓冲”指向离屏目标
GhostFramebuffer.arm();     // 从这一刻起 MinecraftClient.getFramebuffer() 返回离屏目标

// 4) 同样的一帧，再渲染一遍
renderer.renderWorld(tickDelta, limitTime, matrices);

// 5) 全部还原
GhostFramebuffer.disarm();
if (previous == null) pipelines.remove(dim); else pipelines.put(dim, previous);
((PipelineManagerAccessor) pm).shaderflash$setPipeline(previous);
client.chunkCullingEnabled = previousCulling;
((WorldRendererAccessor) client.worldRenderer).shaderflash$setFrustum(previousFrustum);
```

为什么第 3 步换成 `getFramebuffer()` 就能把整条输出链改道：

* `WorldRenderer.render` 开头就是用 `MinecraftClient.getFramebuffer().beginWrite(...)` 绑定目标；
* Iris 的 composite / final pass 也走 `Minecraft.getInstance().getMainRenderTarget()`（= Yarn 的
  `getFramebuffer()`）；
* Iris 判断“主缓冲是否绑定”（`shouldOverrideShaders()`）时，比较的也是这个方法返回的对象，
  所以状态判断会跟着一起自洽；
* 离屏 FBO 是一块真正的 `SimpleFramebuffer`，内容不受 `swapBuffers` 影响，也永远不上屏。

离屏目标的尺寸：**首帧预热**用与真主帧缓冲一致的尺寸（免得白重建一次）；
**副渲染截图（自定义分辨率）的预热帧与快门帧**都用目标分辨率 —— 这时 Iris 会按该尺寸
重建这条管线自己的渲染目标，所以是真正的目标分辨率渲染。**真实主帧缓冲全程保持窗口尺寸。**

为了让原版那些按窗口尺寸取尺寸的东西也在这一遍里按目标尺寸工作，这一遍要做两件事：

1. 让 `Window` 上报目标尺寸（原版的视口与投影都取自它）；
2. 用 `WorldRenderer.onResized(目标尺寸)` 把原版的两个后期处理缓冲（实体描边 / 观察者透明）
   调到同一尺寸 —— 它们的 pass 会设置一个“自己缓冲尺寸”的视口，而原版渲染完并不还视口
   （`WorldRenderer.render` 里 `entityOutlinePostProcessor.render(...)` 之后只
   `getFramebuffer().beginWrite(false)`），于是紧随其后的手部会按窗口分辨率落位。
   这是 0.2.2“高清图上手部错位”的根因，0.2.4 用这一条从副管线侧修掉。

> 0.2.3 起还有一道 `ViewportGuard`（`ViewportGuardMixin` 挂在
> `GlStateManager._viewport`）：副渲染那一遍里若有谁把视口设回窗口尺寸，
> 会被改写成这一遍真正的目标尺寸。它现在是**保险**（上面那条才是根治），
> 命中次数会写进日志、预期为 0。

## 4. 注入点清单

所有对 Minecraft 类的注入点都写成 **intermediary 名 + `remap = false`**：本工程手工构建、
没有 Mixin 注解处理器生成的 refmap，运行时只认 intermediary 名。

| Mixin | 目标 | 成员 | 作用 |
| --- | --- | --- | --- |
| `MinecraftClientMixin` | `net.minecraft.class_310` | `method_1522`（`getFramebuffer`）HEAD，cancellable | 离屏渲染期间把主帧缓冲换成模组自己的离屏目标 |
| `ViewportGuardMixin` | `com.mojang.blaze3d.platform.GlStateManager` | `_viewport`（IIII）HEAD，cancellable | 副渲染那一遍里把“设回窗口尺寸”的视口改写成本遍目标尺寸 |
| `GameRendererAccessor` | `net.minecraft.class_757` | `field_3992`（`renderHand`） | 预热帧临时关掉手部渲染 |
| `GameRendererMixin` | `net.minecraft.class_757` | `method_3188`（`renderWorld`）HEAD + TAIL | HEAD：抓入口姿态 + 截图取景；TAIL：新管线建好后补渲染一帧 |
| `WorldRendererAccessor` | `net.minecraft.class_761` | `field_27740`（`frustum`） | 保存/还原视锥体 |
| `PipelineManagerMixin` | `PipelineManager` | `destroyPipeline` TAIL | Iris 重载后释放副管线 |
| `PipelineManagerAccessor` | `PipelineManager` | `pipeline`、`pipelinesPerDimension`、`versionCounterForSodiumShaderReload` | 偷换当前管线、让 Sodium 重建地形着色器 |
| `IrisAccessor` | `Iris` | `currentPack`、`currentPackName` | 主副互换后同步 Iris 自己的状态 |
| `IrisRenderingPipelineAccessor` | `IrisRenderingPipeline` | `initializedBlockIds`、`pack` | 阻止副管线改写全局材质表并触发全区重建 |
| `SodiumTerrainProgramsMixin` | `IrisChunkProgramOverrides` | `getProgramOverride`、`deleteShaders`、`@Shadow programs/shadersCreated` | 让 Sodium 地形着色器在主副之间零成本切换 |

`SodiumTerrainProgramsMixin` 由 mixin 配置插件 `DuoMixinPlugin` 条件加载：没装 Sodium、
或这个 Iris 版本没有 Sodium 兼容层时直接跳过。

## 5. 全局状态这件麻烦事

Iris 大部分状态都在管线实例里，但有一个例外：`WorldRenderingSettings.INSTANCE` 是**全局单例**，
存着方块材质 ID 表、实体/物品 ID 表、AO 等级、是否体素化光源方块、是否使用扩展顶点格式等等。
Iris 的前提是“同一时刻只有一条管线”，所以它随便写。

第二条管线一创建就踩了这个前提，本模组用三招处理：

1. **创建副管线前拍快照，创建后还原。** `WorldSettings.capture()/restore()` 把上面这些值
   取出来、建完副管线再写回主管线那份，并 `clearReloadRequired()`（否则 Iris 会在下一帧
   重建全部区块网格，代价极大）。
2. **不让副管线碰材质表。** `IrisRenderingPipeline.beginLevelRendering()` 第一次被调用时会
   用**当前包**的材质表覆盖全局并调用 `WorldRenderer.reload()` 全区重建。我们在建好副管线后
   立刻把它的 `initializedBlockIds` 置为 `true`，这段逻辑就不会执行 —— 副管线那一遍
   完全按主管线的材质表渲染。
3. **提升主副时显式应用新主管线的设置**（`WorldSettings.applyFor(...)`）。这时材质表如果
   真的不同，就让它照常触发一次区块重建，保证画面正确。

由此得到一个必须说清楚的限制：**方块材质 ID 写进区块顶点，是全区共享的**。两包的
`block.properties` 映射不同时，副管线那一遍读到的 ID 来自主管线，材质判断会偏。
因为那一遍不上屏，所以只是“预热得不够真”；但真正切过去时必须重建一次区块网格才完全正确。
设置界面的“兼容性自检”会直接比较两包的 ID 表并给出提示。

## 6. Sodium 地形着色器：两份缓存

装了 Sodium 时，区块地形由 `IrisChunkProgramOverrides` 负责编译，它内部只有**一份**
`programs` 表，而且只在“版本计数器变化”或“渲染器重建”时才重编。换管线后它会继续拿着
主包的地形程序去画副管线的画面 —— 结果就是每次切换都要重编一遍地形着色器。

本模组给每条管线各留一份编译结果：

* `getProgramOverride` 头部先看“当前管线”是不是和 `programs` 表的主人一致；
* 不一致就把当前那份整体搬进缓存（`EnumMap` 拷贝），再把目标管线那份搬出来；
* 目标管线还没有缓存时，保持 `shadersCreated = false`，让 Iris 正常编译一份并缓存；
* Iris 自己调用 `deleteShaders()`（真正的重载/换维度）时，把缓存整体删掉、状态归零；
* 缓存里的程序已经不在 Iris 的表里，所以由本模组负责 `delete()`，不会重复删除。

## 7. 主副互换（F7）

```java
pipelines.put(dimension, incoming.pipeline);      // Iris 按维度取管线的地方
accessor.shaderflash$setPipeline(incoming.pipeline);  // 当前管线
IrisState.setCurrentPack(incoming.pack);          // Iris 自己记录的“当前包”
IrisState.setCurrentPackName(incoming.name);
WorldSettings.applyFor(incoming.pack, incoming.pipeline, dimension, true);
accessor.shaderflash$setVersionCounter(accessor.shaderflash$getVersionCounter() + 1);  // 让 Sodium 重编地形程序
Iris.getIrisConfig().setShaderPackName(incoming.name);
Iris.getIrisConfig().save();                      // 重启后保持选择
```

然后把原来的主管线对象直接留作新的副管线 —— 于是**反向切换同样零编译**。
`IrisState` 优先走 mixin 生成的 accessor 写 `currentPack` / `currentPackName`，
万一 accessor 没被应用则退回反射，避免互换后 Iris 的认知和实际管线不一致。

## 8. 资源生命周期与安全阀

| 时机 | 动作 |
| --- | --- |
| 进入世界 + 开启双管线 | 预编译副管线（一次性开销，会有一小段卡顿） |
| `PipelineManager.destroyPipeline()`（Iris 重载/换维度） | 销毁副管线，下一个 tick 自动重建 |
| 关闭开关 / 离开世界 | 销毁副管线（`pipeline.destroy()` + 关闭 zip 文件系统） |
| 副渲染抛异常 | 捕获、还原状态、停用副渲染并在聊天框说明 |
| `getFramebuffer()` 重定向没生效 | 判定注入失效，立即停用副渲染（避免画面反复闪） |
| 设置界面 | 可手动“解除副渲染停用” |

副管线的渲染只在**客户端 tick** 里创建、只在**世界渲染尾部**使用，绝不在渲染中途构造 GL 资源。
