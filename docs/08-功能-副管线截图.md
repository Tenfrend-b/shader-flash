# 功能：副管线截图

> 说明：本文里的 `1.x` 是**开发期间的临时迭代号**，对外版本号为 **0.1**（见 [`../CHANGELOG.md`](../CHANGELOG.md)）。

> **本文的当前状态（0.2.2）**：流程是「**帧首用副管线渲染一遍 → 立刻读像素 → 本帧正常渲染覆盖掉它**」。
> 画到哪里由 `screenshotLongEdge` 决定：**跟随窗口**（默认）写进主帧缓冲；
> **高清档位**写进模组自己的离屏目标（尺寸 = 目标分辨率，主帧缓冲不动）。
> 0.1.8/0.1.9 直接读常驻离屏 FBO 时拿到过“只有天空底色 / 没走完 final”的画面，
> 根因是当时渲染前没有先换绑目标，已由 `target.beginWrite(true)` 修掉，见下面「实现要点」。
> 更下面“1.4.0 / 1.4.1 的切屏实现”保留为历史记录（它解释了按键时序这个坑，那条结论依然成立）。

## 它做什么

打开后**接管原版的 F2**：不再截“屏幕上那条管线”的画面，而是
**把材质表切到副包 → 等地形重建完 → 先渲染若干帧预热 → 用副管线渲染一遍并立刻读像素 → 还原材质表**。

因此：

* **取景那一帧你看不到**：它发生在这一帧的最开头，本帧随后的正常渲染会把痕迹覆盖掉，
  截图本身不阻塞、也不改变主画面的分辨率与内容；
* **但“完全没有任何痕迹”并不成立**：两包的材质表不一致时，重建期间屏幕上的地形会
  跟着换成副包的材质分类（单套区块网格的固有限制）。0.1.x 的文档把它写成“不切屏、
  不闪屏”，那是相对最初那版“切屏拍摄”而言的，现在这句话已经删掉；
* 截图规则不变：存到原版 `screenshots/` 目录，聊天框也会照常提示 "Saved screenshot as …"。

> 注：切屏版还会连 HUD 一起拍进文件；现在文件里是**纯世界画面**（取景在 HUD 之前）。

## 分辨率：副渲染截图可以是高清的（0.2.2 起，0.2.3 重做输入方式）

设置界面「副管线截图」一节里有两个文本框 **截图宽度 / 截图高度**（配置字段
`screenshotWidth` / `screenshotHeight`），下面是两个按钮：

* **按窗口宽高比补全高度**：用宽度 + 窗口宽高比算出高度，填进高度框；
* **按窗口宽高比补全宽度**：反过来。

两个框都留空 = **跟随窗口分辨率**（默认，渲染进主帧缓冲，行为与旧版一致）。
只填一边时，另一边在算目标尺寸时也会按窗口宽高比自动推出；两边都填就按填的来
（想拍宽幅/竖幅才需要这样）。单边下限 64（再小没有意义）、上限 16384（超过 GL 常见的
`GL_MAX_TEXTURE_SIZE` 就建不出目标了）。

> **像素总量只是警告，不是限制**：超过约 33M（7680×4320）时界面会给一行提示、
> 日志里也会写一条 WARN，但仍然按玩家填的尺寸渲染 —— 超量渲染是玩家的选择，
> 失败或慢到无法接受的风险由玩家自己承担。目标建不出来时（显存不足 / 超过 GL 上限）
> 这一次截图会退回窗口分辨率，并在日志里说明原因。

渲染方式（0.2.4 起：**只动副管线自己的目标，真实主帧缓冲一个像素都不改**）：

* **预热帧与快门帧都渲染进副管线自己的离屏目标**，尺寸 = 目标分辨率；
  Iris 判断“当前是不是主缓冲”用的是 `MinecraftClient.getFramebuffer()`（见 Iris 的
  `MixinRenderTarget`），而这个调用在离屏渲染期间被本模组接管，所以 begin/composite/final
  全都照着这块离屏目标走 —— 与画进主帧缓冲语义相同，只是分辨率不同；
* 两遍用**同一个目标、同一个分辨率**：Iris 在尺寸变化时会重建渲染目标，那会把光影包累积的
  “人眼适应”历史清掉，正好又拍成偏黑的一张；
* 为了让原版那些“按窗口尺寸取尺寸”的东西在这一遍里也按目标尺寸走，这一遍要做两件事：
  ① 让 `Window` 上报目标尺寸（原版的视口与投影都取自它）；
  ② 用 `WorldRenderer.onResized(目标尺寸)` 把原版的两个后期处理缓冲（实体描边 / 观察者透明）
  也调到目标尺寸 —— 见下面「视口护栏」；
* **预热帧不画手部**（`GameRendererAccessor` 临时把 `renderHand` 关掉）：手部对光影包的
  时域适应没有意义，留着只是多一份开销。

### 视口护栏（0.2.3 新增）

0.2.2 的高清档位把副管线渲染进一块更大的离屏目标，结果**手部只按窗口尺寸画出来、
还挤在左下角**。逐像素比对可以定量确认：手部在图里的位置与像素尺寸，正好等于
「用窗口尺寸的视口、锚在左下角」画出来的结果 —— 也就是渲染途中有人把视口
（`glViewport`）设回了**窗口尺寸**，之后画的手部就按窗口分辨率落位。

真凶是**原版的实体描边后期处理器**：它的缓冲在资源加载时按窗口尺寸创建，
它的 pass 会设置一个“自己缓冲尺寸”的视口，而原版渲染完并不还视口 ——
`WorldRenderer.render` 里那段是
`entityOutlinePostProcessor.render(...)` 紧接着 `getFramebuffer().beginWrite(false)`
（`beginWrite(false)` 不设视口），而手部就在这之后由 `GameRenderer.renderHand` 画。

所以修法是**从副管线侧对齐尺寸**：这一遍用 `WorldRenderer.onResized(目标尺寸)`
把那些后期处理缓冲一起调到目标尺寸（渲染完再调回窗口尺寸）。这样它们的 pass 设置出来的
视口本来就是目标尺寸，手部自然落位正确，而且**完全不需要碰主帧缓冲**。

此外还留了一道 `ViewportGuard`（`ViewportGuardMixin` 挂在 `GlStateManager._viewport`）作为保险：
副渲染那一遍里若有谁再把视口设成“窗口尺寸”，会被改写成这一遍真正的目标尺寸；
其它尺寸（Iris 的 composite `viewportScale`、阴影贴图分辨率、1×1 的取中心深度）一律不动。
命中次数会写进日志 —— **预期是 0 次**（根因已由 `onResized` 修掉），一旦出现就说明还有别的来源。

## 打开方式

设置界面（F8 或 Mod Menu 齿轮）→ **副管线截图（F2 用副管线）**，默认关闭。
关闭时 F2 完全按原版行为工作。

## JPG 模式（压缩截图，0.3.1 新增）

同一节里的开关 **「JPG 模式（压缩截图）」**（配置字段 `screenshotJpg`，默认关）：

* 关：与 vanilla 一致，写成**无损 PNG**（`ScreenshotRecorder.saveScreenshot`）；
* 开：写成 **JPG，质量 85%**（`JpegScreenshot`），文件名后缀 `.jpg`，体积明显更小，
  代价是有损压缩（高对比边缘能看到压缩痕迹，适合发聊天软件/论坛）；
* 两者的**像素来源完全相同**：都走 `ScreenshotRecorder.takeScreenshot(framebuffer)`
  （把当前帧缓冲的颜色附件读成 `NativeImage`），区别只在编码这一步；
* 编码与写盘都在 IO 工作线程上做（`Util.getIoWorkerExecutor()`），渲染线程只负责读像素，
  所以 8000×4000 这种大图也不会卡住游戏；
* 完成提示带“点开文件”的点击事件，方便直接打开；失败时走 `MESSAGE_SCREENSHOT_FAILED`。

> 注意：`NativeImage` 的字节顺序是 **RGBA**（`Format.RGBA` → `GL_RGBA`，
> `takeScreenshot` 之后已经做过垂直翻转），JPEG 转换就按这个顺序读，不要想当然按 BGRA。

## 实现要点

| 步骤 | 挂点 | 说明 |
| --- | --- | --- |
| 拦下原版 F2 | `Keyboard.onKey`（`class_309.method_1466`）里的 `ScreenshotRecorder.saveScreenshot(File, Framebuffer, Consumer)` 调用 | 用 `@Redirect` 换成我们的实现；不满足条件时**原样调用原版方法** |
| 切材质表 | `DuoManager.beginSecondaryCapture()` | 把副包的材质表应用到全局（与 F7 同一套逻辑，含“分离 AO 变化时让地形程序重编一次”），并把视距内的区块网格排队后台重建；**不**动管线指针、**不**动屏幕 |
| 判断时机 | `ScreenshotCapture.shouldShootNow()`（每帧开头询问） | 先过最小等待，再要求 Sodium 构建队列走完一轮「忙 → 空」；**0.2 起没有超时回落，没稳定就一直等**（HUD 有进度条与预热帧数，玩家看得见还差多少） |
| 目标尺寸 | `CaptureResolution.resolve()` | `screenshotWidth`/`screenshotHeight` 都是 0 → 用主帧缓冲（窗口尺寸）；否则算出目标宽高（只填一边时另一边按窗口比例、取偶数，并夹进像素预算） |
| 取景 + 存盘 | `GameRenderer.renderWorld` 开头（`class_757.method_3188` HEAD）→ `DuoManager.captureSecondaryFrame()` | 用副管线把世界渲染一遍（主帧缓冲或按上一条选择的离屏目标），紧接着调用**原版** `ScreenshotRecorder.saveScreenshot` 读它；本帧随后的正常渲染会覆盖掉这一帧，所以玩家看不到 |
| 还原 | `DuoManager.endSecondaryCapture()` | 还原材质表、清掉 `reloadRequired`、让地形重建回主管线的样子 |
| 兜底 | 客户端 tick | 万一一直取不到景（暂停 / 最小化：连续 100 tick 没有渲染帧），就取消本次截图并还原材质表。**0.2 删除了原先的 12 秒回落 / 60 秒硬上限**，只保留这一条；**0.2.1 起这个阈值可调**（设置界面「最大静默等待时间」，100 ~ 32767 tick） |

## 画进主帧缓冲 vs 画进离屏目标

Iris 判断“当前是不是在画主缓冲”用的是 `Minecraft.getInstance().getMainRenderTarget()`
（`MixinRenderTarget`：`this == getMainRenderTarget()`）。本模组的 `MinecraftClientMixin`
在离屏那一遍里接管了这个 getter，让它返回离屏目标 —— 也就是说
**离屏那一遍里 Iris 依然认为自己在画“主缓冲”**，begin/composite/final 那套绑定逻辑照常走。
这一点是 0.2.2 敢把高清截图渲染进离屏目标的依据（`FinalPassRenderer` 也会按当前主目标的
尺寸与颜色附件重新计算，见其 `renderFinalPass()` / `lastColorTextureId` 那段）。

> 历史结论更正：0.1.x 把“离屏截图画面不对（只有天空底色 / 扭曲地形）”归因于上面那个
> 判定，其实真正的原因是**渲染前没有先换绑目标** —— 原版世界渲染开头会 `Render.clear`，
> 清的是“当前绑定”的缓冲，于是要么擦掉主画面、要么目标里只有底色。
> 现在 `renderSecondaryPass` 里第一步就是 `target.beginWrite(true)`，这条已经堵住。

两条路各有取舍：

| 目标 | 何时用 | 说明 |
| --- | --- | --- |
| 主帧缓冲 | 分辨率跟随窗口（默认） | 与“按 F7 切过去”看到的完全同一条路径，最保守 |
| 离屏目标 | 高清档位 | 分辨率可以大于窗口；主帧缓冲不动，但需要接管 `Window` 上报的尺寸（见上文「分辨率」一节） |

不影响的路径：**Ctrl+F2（远景图）** 与 **Shift+F2（超大截图）** 走的是别的函数（4 参数重载与
`takeHugeScreenshot`），保持原版行为不变。

## 已知取舍

* 两包材质表不一致时**必须**重建一次区块网格，而区块网格是全区共享的 ——
  重建期间屏幕上的地形材质分类也会跟着变。这是 Minecraft 单套网格的固有限制；
  两包材质设置一致时完全没有重建，全过程不可见。
* 文件里没有 HUD（见上）。
* 副管线不存在（没开启双管线、没选副包、不在世界里）时，会提示并**回退到原版截图**，不会丢图。
  副管线正在后台预编译时同样回退（提示不同），不会让你干等。

## 等待条件踩过的坑

> **0.1.12 补充**：等待条件再稳也挡不住“新建管线的第一遍渲染”这种情况。玩家实测出现过
> 整张纯黑的截图（采样 10112 点，最大亮度与平均亮度都是 0），特征是副包管线刚建好、
> 此前一帧都没渲染过，而且那次几乎刚到最小等待就被放行。现在截图不再直接调原版
> `ScreenshotRecorder.saveScreenshot`，而是自己 `takeScreenshot` 后**采样检查是否整张纯黑**：
> 纯黑就丢掉这一帧、700 ms 后重拍（最多 5 次），正常才按原版命名规则落盘并发原版提示；
> 连续黑屏则明确告诉玩家“没有保存”，绝不把黑图写进 `screenshots/`。
> 另外，顶点格式不同（一边是「空包」原生管线）时，取景与还原都改走整世界重建并同样等待。

「等地形重建完」这件事在实现上比看起来难，记录一下踩过的坑：

1. **`isTerrainRenderComplete()` 不能直接当“重建完”用**：Sodium 的重建任务是
   *先登记、后入队* 的（`scheduleRebuildForChunk` 只给区块打标记，任务要等 Sodium 下一次
   `update()` 才进队列），所以刚调度完的一瞬间“队列为空”会被误判成“已经做完”。
2. 改成跟踪一轮完整的「忙 → 空」之后，又出现反向的问题：如果重建**快到一个 tick 都没被观测到**，
   `remeshSettled` 会永远停在 false，于是“明明 10 秒就重建完了，却一直在等”。
   现在加了一条：调度后 3 秒内仍没看到队列非空，就认定这一轮已经做完（或压根没排队）。
   （0.1.x 那时还有 12 秒超时回落把这种等待兜走，0.2 删掉超时后，这条判定就是唯一的出口。）
3. 两包材质设置一致时**根本不需要**重建，此时不应进入任何等待 —— 由
   `WorldSettings.MeshState.differences(...)` 先判空。

## （历史）1.4.0 的切屏实现与时序问题

> 下面这节记录的是已被替换掉的“切屏”实现。它解释的两条结论今天仍然有效：
> **按键回调发生在本帧世界渲染之后**、以及**任何“借一帧渲染”的功能都要多等一整帧**。

1.4.0 是「换管线 → 当场在本帧结尾截图」。实际运行时出现：**屏幕看不到切换，文件里也是主管线的画面**。

原因是**按键回调发生的时刻**：GLFW 的按键回调是在这一帧的**世界渲染之后**（呈现那一步顺带泵出事件）才被处理的。
也就是说，收到 F2 时，主帧缓冲里已经是**主管线**刚画完的那一帧：

```
帧 N：世界渲染（主管线） → …… F2 回调：换到副管线 → 帧尾：截图 ← 拍到的是主管线那一帧
      帧尾之后立刻还原 → 副管线一帧都没画过（所以屏幕也看不到切换）
```

修法：换管线后**先跳过当前这一帧**，等一个从头到尾都由副管线渲染的完整帧，再在帧尾截图。
额外好处是屏幕上会真的闪一下副管线的画面（这正是“我截的是哪条管线”的直观反馈）。

设置里新增「**截图层数：先渲染 N 帧**」（默认 2，可选 1/2/3/5/10/20）：N 就是换管线后先渲染多少帧再拍。
调大可以让那次切换更明显（代价是截图动作多花几十毫秒）。
