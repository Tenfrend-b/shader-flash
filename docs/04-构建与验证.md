# 构建与验证

## 1. 两种构建方式

### 方式 A：常规 Loom（有网络时首选）

`source/` 下有标准的 `build.gradle` / `settings.gradle` / `gradle.properties`，
依赖从 Modrinth Maven 与 Terraformers Maven 拉取：

```
cd source
gradlew build        # 产物在 build/libs/
```

### 方式 B：离线手工构建（本次实际使用）

本机沙箱不允许网络，而且 loom 在受限沙箱里会被 `Path.toRealPath()` 挡住（JDK 的 zipfs 不可用），
所以本次交付用的是 `build-offline.ps1`：

```
1) 用 named（Yarn）类路径 javac 编译源码
2) 用 tiny-remapper 把编译结果从 named 重映射到 intermediary
3) 打包成可放进 mods/ 的 jar
```

它依赖 `work/build/` 里预先准备好的东西：

> **重建这个工作区**：`tools/collect_cp.py` 就是当时用来收集类路径的脚本
> （从本地 Gradle / loom 缓存里挑出 `libs-named`、`libs-tools`、`cp-inter`、`cp-named`）。
> Iris 与 Sodium 的 named 副本用 `tools/RemapTool.java` + loom 缓存里的 `mappings.tiny`
> 从玩家 mods 目录里的 jar 重映射得到（intermediary → named）：

```powershell
# 1) 解包 Iris / Sodium 的 jar 到目录（tiny-remapper 在受限环境下只吃目录）
#    并把 META-INF/jars/ 里的嵌套 jar 挪走，否则重映射会去读它们而失败
# 2) 编译 RemapTool
& $java -cp "$libsTools\*" tools.RemapTool <输入目录> named\iris-named.jar `
      $mappings intermediary named $cpInter
```

| 目录/文件 | 内容 | 来源 |
| --- | --- | --- |
| `libs-named/` | Yarn 命名的游戏与库 jar | loom 缓存 + Gradle 模块缓存 |
| `libs-tools/` | tiny-remapper、ASM、mapping-io 等 | Gradle 模块缓存 |
| `cp-inter/` | intermediary 命名的游戏类目录 | loom 缓存里的 `minecraft-merged-intermediary` |
| `cp-named/` | Yarn 命名的游戏类目录 | loom 缓存里的 `minecraft-merged` |
| `named/iris-named.jar` | Iris 从 intermediary 重映射到 named 的副本 | 本机安装的 `iris-1.7.1+mc1.20.4.jar` |
| `named/sodium-named.jar` | Sodium 的同上副本 | 本机安装的 `sodium-fabric-0.5.8+mc1.20.4.jar` |
| `tools/classes/` | 编译好的 `tools.RemapTool` | `tools/RemapTool.java` |

两个沙箱“怪现象”都不影响结果：javac 收尾时会因为没法 `toRealPath` 打印一段崩溃报告（产物已经
写好），tiny-remapper 读输入时要用目录而不是 jar。脚本里都做了对应处理。

## 2. 验证：校验器做了什么

`tools/VerifyTool.java` 对**重映射之后的成品 jar** 做四项检查，类路径使用**运行期真实的命名空间**
（游戏类的 intermediary 目录、真实的 Iris jar、Sodium jar、Fabric API 与 Mod Menu）：

1. **Mixin 目标类**：`@Mixin` 指定的类在类路径里存在；
2. **注入点成员**：`@Inject` 的方法名、`@Accessor` 的字段名、`@Shadow` 的字段名都存在；
3. **描述符一致性**：把注入处理器的参数表（去掉末尾的 `CallbackInfo`）与目标方法的参数表逐项比较 ——
   参数写错会让注入静默失败，这是最容易犯又最难发现的错误；
4. **引用完整性**：模组字节码里出现的每个类引用都能在运行期类路径中解析（等于检查“没有把
   named 名误写进成品”）。

运行方式（`libs-tools/`、`cp-inter/` 等见上一节）：

```
java -cp "libs-tools/*;tools/classes;libs-named/sponge-mixin-*.jar" tools.VerifyTool \
shader-flash-0.1.jar cp-inter <iris jar> <sodium 目录> <fabric-api 各模块> <libs...>
```

## 4. 验证的边界（必须说明）

* 校验器检查的是**注入能不能成立、引用能不能解析**，不是“运行时行为一定正确”。
  真正跑起来之后的画面、性能，以及 Iris 内部状态是否符合预期，需要在客户端里实测。
* 本机没有条件启动 Minecraft（无网络、受限沙箱），所以本次没有做进游戏实测。
* 模组内置了运行期自检作为补偿：若主帧缓冲重定向没生效或副渲染抛异常，会自动停用副渲染
  并在聊天框说明原因，不会把画面弄花。
