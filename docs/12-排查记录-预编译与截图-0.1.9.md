# 0.1.9 / 0.1.10：预编译、截图取景 与 阴影目标 的设计与取舍

本文记录两件事的**决策依据**：为什么“后台预编译”只能做到这一步，
以及“副管线截图”为什么改成了读离屏帧缓冲、又为什么仍可能看到地形变化。

## 一、后台预编译：能移的移走，不能移的说清

### 1. 一次预编译的三段开销

| 阶段 | 做什么 | 能离开渲染线程吗 |
| --- | --- | --- |
| 解包 | 把 zip / 目录铺成 `config/shaderflash/packcache/<包名>/` | **能**（纯文件 I/O） |
| 解析 | 读 `shaders.properties` / `block.properties`、构建 `ProgramSet` | **基本能**（纯 CPU 文本处理），见下面的例外 |
| 编译 | `new IrisRenderingPipeline(programSet)` | **不能**（GL 只属于渲染线程） |

实测数字（玩家日志，0.1.7）：Photon 6912 ms、iterationT 4275 ms、MakeUp 1721 ms。
这些数字里有多少是“解包 + 解析”，要看下一版运行日志里的分段统计：

```
[ShaderFlash] 副管线 X 预编译完成，总用时 N ms（解包 A ms / 解析 B ms / 编译 C ms）
```

### 2. 为什么编译那一段切不开

Iris 的 `IrisRenderingPipeline` 构造函数是一条**不可中断的长链**：

* `ShaderMap` 在构造函数里对**每一个** `ShaderKey` 调一次工厂，当场编译 + 链接；
* `CompositeRenderer`（begin / prepare / deferred / composite）在构造函数里对
  每一个 pass 调 `createProgram(...)`，同样当场编译；
* 阴影程序、setup、final pass 也是同一批。

想在两帧之间“暂停”这条链，只有两条路：

1. **fork 它的构造流程**：把上面这些 `new` 改成“可恢复的步骤”。
   麻烦在于 `Program` 是 **final 类**、`ShaderMap` 的循环在构造函数里、
   各 render target/缓冲区在构造期就与管线互相引用，等于重写 Iris 的初始化层。
2. **GL 调用转发**：把构造过程放到工作线程，所有 GL 调用转发到渲染线程、每帧限量执行。
   需要在 Iris 与 Mojang 的所有 GL 调用点（`IrisRenderSystem`、`GlStateManager`、
   直接调 LWJGL 的地方、`ProgramBuilder`、`GlSampler`…）插入转发层，而且失败模式是
   “驱动层崩溃”而不是“抛异常”。风险与收益不成比例。

`GL_KHR_parallel_shader_compile` 也解决不了这个问题：它只在**同一条线程一次发多个编译**时
才有并行收益，而 Iris 是一个程序一个程序地“编译 → 链接 → 取 uniform”，中间夹着依赖关系。

所以 0.1.9 的做法是：**把前两段移出渲染线程，让它们不再叠加到那次卡顿上**，
并把进度实时显示出来（界面状态区 + HUD），同时给玩家一个更好的等待体验
（预编译期间按 F7 会记下意图，编译一完成自动完成切换）。

### 3. 工作线程上的红线

| 红线 | 具体表现 | 我们的处理 |
| --- | --- | --- |
| 不能做 GL 调用 | `StandardMacros.createStandardEnvironmentDefines()` 会 `glGetString` / `glGetStringi` 问版本与扩展 | **在启动预编译时（渲染线程）先算好**，把 `ImmutableList<StringPair>` 存进任务对象 |
| 解析期可能查 GL 能力 | `ShaderProperties` 处理 `blend.<pass>.<buffer>` 时调 `IrisRenderSystem.supportsBufferBlending()` → `GL.getCapabilities()` | 后台抛错就**自动退回渲染线程重跑一次**，并打一条 warn 日志 |
| 不能碰 Iris 全局状态 | `WorldRenderingSettings` / `ImmediateState` / 管线字段 | 后台阶段完全不碰；编译阶段本来就在渲染线程，且沿用 0.1.6 起的“构造前后快照 / 还原” |
| 要安全发布结果 | 工作线程写 `pack`，渲染线程读 | 用 `volatile boolean parsed` 作为发布标志（写在前、读后） |

## 二、副管线截图：为什么不切屏、以及为什么还可能看见地形变化

### 1. 切屏版的问题

0.1.7 及以前：`beginScreenshotSwap()` 把“当前管线 + 按维度缓存 + `Iris.currentPack(Name)`”
全换成副包，屏幕上会**闪一帧**副管线的画面，再由 `endScreenshotSwap()` 换回来。

问题是这段代码要额外处理一堆全局状态（视锥体、遮挡剔除、`ShadowRenderer.ACTIVE`），
任何一处漏还原都会污染主管线（0.1.1 就吃过一次视锥体的亏）。

### 2. 不切屏版

离屏 FBO 里的像素本来就是“副管线渲染的一整帧”，所以**根本不用动屏幕**：

```
FrameBuffer ghost = GhostFramebuffer.target();     // 副管线那一遍的输出
ScreenshotRecorder.saveScreenshot(dir, ghost, receiver);   // 原版函数，只是换了个 FBO
```

于是：不切屏、不闪回、不碰管线指针，删除了一大类全局状态还原的坑。

### 3. 为什么还要“切材质表 + 等地形重建”

区块顶点里烘焙的方块材质 ID 是**全区共享**的（`WorldRenderingSettings` 是全局单例，
Sodium 的 `ChunkBuildBuffers` 还把它捕获一份）。副管线那一遍虽然用的是副包的着色器，
但顶点里的材质 ID 来自当前主管线 —— 两包材质映射不同时，截图里就会出现
“副包的着色器 + 主管线的材质分类”。要等价于“用副包玩这个画面”，只能和 F7 一样：

1. 把材质表切到副包（`WorldSettings.applyFor`）；
2. 如果两包在“会被烘焙进网格”的设置上有差异，就让地形按新表重建
   （`SodiumRemesh`，高优先级、由近到远）；
3. 等重建做完（Sodium 构建队列走完一轮「忙 → 空」）；
4. 拍离屏 FBO；
5. 还原材质表 + 把地形重建回主管线的样子。

**代价**：第 2 步期间屏幕上的地形材质分类也会跟着变（因为网格只有一套）。
两包材质设置一致时（`MeshState.differences()` 为空）完全没有这一步，全过程不可见。
要彻底消灭这个现象，需要 Iris/Sodium 层面支持“每条管线各一套区块网格”，
超出本模组能改的范围 —— 已记在 [`03-限制与风险.md`](03-限制与风险.md)。

### 4. 「仅预编译」模式下 FBO 是空的

> **0.2.2 更新**：下面描述的“渲染模式 / 开界面时暂停”两个开关已经删除，
> 副管线平时完全不渲染，取景那一帧由模组主动拉起 —— 这正是本节结论的自然延伸。

这是玩家指出的漏洞，修法是在截图期间**主动拉起**幽灵那一遍：
`DuoManager.onWorldRenderTail` 里 `forScreenshot = ScreenshotCapture.isPending()`
会绕过“渲染模式”的判断（`仅预编译` 本来直接 return）与“开界面时暂停”，
于是每帧都会渲染一遍副管线，FBO 里一定是最新画面。

## 三、等待条件的三个坑（复现了两次）

1. **“队列为空”≠“重建完”**：Sodium 的任务是先登记后入队，刚调度完的一瞬间队列是空的。
   → 改成跟踪一轮完整的「忙 → 空」。
2. **太快也会出问题**：如果重建快到一个 tick 都没观测到队列非空，
   `remeshSettled` 会永远停在 false，表现为“明明早就重建完了却一直等到超时才拍”。
   → 加一条：调度后 3 秒仍没看到队列非空，就认定这一轮已经做完（或压根没排队）。
3. **根本不需要重建的场合也在等**：两包材质设置一致时不该进入任何等待。
   → 先判 `MeshState.differences()` 是否为空。

## 四、验证方式

* 编译期：`build-local.ps1`（javac → tiny-remapper → `VerifyTool`）全绿；
* 设计层面无法离线验证的部分（帧率、重建耗时、画面）依赖游玩测试，
  日志里会打印分段耗时与等待原因，便于继续定位。

# 0.1.10 的两处修正（都来自玩家实测反馈）

## 五、副管线截图：为什么要改走「真实像素路径」

0.1.8 / 0.1.9 是直接读**离屏 FBO** 的（幽灵渲染那一遍写出来的那块）。玩家实测发现画面不总是对的：

* 两张 Cyanide 副包的截图是**纯色**（两次颜色不同、都是干净的单色 —— 整张图只有天空，没有地形）；
* 一张 Photon 副包的截图是**没走完 composite/final 的中间态**（天空位置出现扭曲的地形）。

**成因**：离屏那一遍会让 `MinecraftClient.getFramebuffer()` 返回另一块缓冲，而 Iris 内部多处用
“当前这个缓冲是不是主缓冲”来判断流程走向 —— `MixinRenderTarget`（Iris 的 `state_tracking`）
直接拿 `this == Minecraft.getInstance().getFramebuffer()` 判定，据此决定 begin/composite/final
那套绑定逻辑怎么走。结论：**离屏那一遍的像素 ≠ 这条管线当主管线时的画面**。

**修法（0.1.10）**：取景改到**一帧的最开头**（`GameRenderer.renderWorld` HEAD）——
用副管线把世界渲染进**主帧缓冲**，紧接着读像素存盘；本帧随后的正常渲染会把它整个覆盖掉，
玩家一帧都看不到。也就是“像素走和按 F7 切过去完全相同的路径”，而“不可见”由**时机**保证，
不再依赖读另一块缓冲。

代价：文件里不含 HUD（取景发生在 HUD 之前）。

## 六、切到 MakeUp 闪退：Iris 的阴影目标是懒创建的

崩溃栈（玩家报告）：

```
NullPointerException
  at IrisRenderingPipeline.lambda$new$6(IrisRenderingPipeline.java:351)  ← requireNonNull(shadowRenderTargets)
  at SodiumTerrainPipeline.initTerrainSamplers
  at IrisChunkShaderInterface.<init>
  at IrisChunkProgramOverrides.createShader   ← Sodium 懒编译地形程序
```

Iris 的阴影渲染目标只在两种情况被创建：

1. `shaders.properties` 里显式写 `shadow.enabled = true`（构造期立刻建）；
2. 某个**非 Sodium 版程序**在编译绑定采样器时发现它要用 `shadowtex*`（`addGbufferOrShadowSamplers`）。

Sodium 的地形程序是**懒编译**的，`createTerrainSamplers` 里直接 `requireNonNull(shadowRenderTargets)`，
Iris 的注释写着“非 Sodium 版早编译过了，所以这里不可能是 null”。
MakeUp 恰好让这个前提不成立：它**没有** `shadow.enabled`，但 `lib/config.glsl` 默认
`#define SHADOW_CASTING`，地形着色器里确实声明了 `shadowtex` —— 于是 NPE。

**修法**：构造完副管线后补一步 `ensureShadowTargets()`：如果这个包**确实带阴影程序**
（`ProgramSet.get(ProgramId.Shadow)` 非空）而阴影目标还没建，就调 Iris 自己的
`shadowTargetsSupplier.get()` 建出来（通过 `IrisRenderingPipelineAccessor` 的 `@Accessor`）。
没有阴影程序的包不补，不白占显存。日志会打印
`副管线阴影渲染目标：已就位/缺失，阴影程序：有/无`，便于核对。

## 七、预编译：解包进后台，解析与编译留在渲染线程

0.1.9 曾试图把“解包 + 解析”都放工作线程。三种真实光影包的日志都显示解析失败：

```
[ShaderFlash] 后台解析失败（java.lang.IllegalStateException: Rendersystem called from wrong thread）
```

Iris 解析 `shaders.properties` 时会做 GL 查询，所以解析也必须在渲染线程。
现在明确拆成「解包 → 工作线程」「解析 + 编译 → 渲染线程」，收益是首次使用某个包时
省掉解包那几秒，而不是一次失败的尝试再回退。
